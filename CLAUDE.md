# nuxt-ui-ds

Публичный репозиторий: github.com/NoNameItem/nuxt-ui-ds. Проект делает одно: из
установленной версии `@nuxt/ui` собирает пакет, из которого Claude Design генерирует
дизайн-кит, выгружает готовый кит с платформы в `kit/` и машинно проверяет, что кит совпал
с библиотекой. Nuxt нужен ради `nuxt prepare` (темы в `.nuxt/ui/*.ts`) и стенда визуальной
сверки.

Кит держится на последней версии Nuxt UI и общий для всех проектов. Проектные
переопределения из `app.config.ts` в кит не попадают: кит равен чистой библиотеке,
переопределения применяются в рантайме поверх.

## Раскладка

| Папка | Что | Документы |
|---|---|---|
| `kit/` | кит побайтно, как на платформе; пишет только `pnpm kit:release` | — |
| `pipeline/` | пакет для генерации, выгрузка кита, приёмка тем | RU, `pipeline/README.md` |
| `bench/` | стенд визуальной сверки: приложение, артборды, реестр | RU, `bench/README.md`, `bench/rounds.md` |
| `README.md`, `docs/import.md`, `NOTICE.md` | пользователю | EN |
| `journal/` | приватный журнал, в git не идёт | RU |

Корень Nuxt — корень репозитория (`srcDir: 'bench/app'`, `dir.public: 'bench/public'`),
поэтому `.nuxt/ui` лежит там же, где читает его `pipeline/build-ds-bundle.mjs`. Связей между
`pipeline/` и `bench/` три, они перечислены в README обеих частей.

## Конвейер

Порядок обязателен — каждый шаг читает выход предыдущего.

```bash
pnpm nuxt prepare                   # .nuxt/ui/*.ts — темы, .nuxt/ui.css — палитра
pnpm build:ds                       # dist/nuxt-ui-<version>-ds.zip — пакет для генерации
KIT_SERVE_URL=… pnpm kit:pull <л.>  # dist/kit-live — рабочая копия кита с платформы
pnpm build:docs                     # dist/docs — doc-страницы кита
pnpm audit:kit                      # dist/audit — отчёт приёмки
pnpm test                           # node:test, pipeline/tests и bench/tests
```

- `build:ds` **стирает `dist/work` целиком** — не класть туда ничего своего.
- `audit:kit` без готового `dist/docs` не запустится: он читает `dist/docs/themes.json`.
  Тесты покрытия в этом случае не падают, а молча пропускаются через `t.skip`.
- Статику кита и манифест приёмка, doc-страницы и съёмка `--local` читают из
  `dist/kit-live/`, а его пишет только `kit:pull`. Подробности выгрузки —
  `pipeline/README.md`.
- Ожидание в приёмке **никогда не строится из исходников кита** — только из библиотеки
  в `node_modules/@nuxt/ui`, из `themes.json` и настоящего `tailwind-variants`. Иначе
  кит проверяется сам собой и сходится всегда.

## Что не коммитится

Всё содержимое `dist/` — производное и пересобирается: пакет, `dist/docs`, отчёты
приёмки, ручные снимки прогонов, выгрузки кита. Поэтому `.gitignore` игнорирует `dist/`
целиком, а не по подкаталогам: пока правила перечисляли подкаталоги, каждый новый
(`dist/probe`, выгрузка кита) оказывался мимо них.

`journal/` — приватный журнал без своего git: промпты раундов, отчёты прогонов, спеки и
планы, id проектов Claude Design (`journal/projects.md`), частные шаблоны сканера, bundle
старой истории. **Спеки, планы и промпты раундов пишутся в `journal/`, а не в `docs/`** —
`docs/` публичный; скилы superpowers по умолчанию пишут в `docs/superpowers/`, поэтому путь
указывать явно. Ссылки на журнал из публичных файлов в публичном дереве ведут в никуда — это
известно и допустимо.

`.beads/`, `.agents/`, `.codex/`, `.claude/`, `AGENTS.md` — локальные настройки
инструментов. Хуки beads работают через `core.hooksPath .beads/hooks` и из игнорируемой
папки.

URL платформы с токенами (`serve_url`) в репозиторий не попадают ни в каком виде;
`kit:pull` и `kit:release` берут адрес только из `KIT_SERVE_URL`. Всё, что отдаёт
`git ls-files`, в каждом `pnpm test` проверяет сканер `pipeline/tests/publish-scan.test.mjs`;
частные шаблоны — `journal/scan-patterns.txt`.

## Git

Remote `origin` — github.com/NoNameItem/nuxt-ui-ds, публичный: всё, что коммитится,
публикуется. Пуш — только после явного подтверждения человека. Почта коммитов задана
локально (`git config user.email`); адрес в файлы не пишется — его поймал бы сканер.
Сообщения коммитов русские, с conventional-префиксом:
`feat(audit):`, `docs(kit):`, `fix(docs):`. `kit/` коммитится отдельным коммитом после
`kit:release`. `bd dolt push` по-прежнему без адреса.

Выпуск — аннотированный тег по версии `@nuxt/ui`, которую воспроизводит кит: `v4.11.1`,
в сообщении тега — дата выгрузки с платформы. Ставится на коммит, в котором `kit/` и
документы уже согласованы, пушится отдельно и тоже только с подтверждения. Опубликованный
тег не двигается: повторный выпуск на той же версии Nuxt UI — `v4.11.1-2`, `v4.11.1-3`.

## Работа с Claude Design

Кит генерирует платформа, и почти всё знание в этом разделе получено дорого.

**Итеративная отладка — на локальной копии, финальная приёмка — на самом ките.**

Отлаживать через `serve_url` невозможно: когда страница виснет, браузер не доходит до
`document_idle` — недоступны ни консоль, ни DOM, ни скриншот, ни в headless Chrome, ни
в расширении. На локальной копии та же причина находится бисекцией за минуты. Копию
собирает `assembleLocalKit` (`pipeline/audit/local-kit.mjs`) и отдаёт свой статический
сервер на случайном порту.

Но копия — это кэш, и он протухает. Статика кита — `dist/kit-live/`, её пишет
`pnpm kit:pull`, и живёт она до следующей выгрузки. **После каждого раунда правок кита её
надо перевыгрузить** — иначе приёмка показывает расхождения, которые в ките уже исправлены,
и отличить их от настоящих нельзя. На это уже напарывались. Поэтому подтверждать результат
по копии нельзя: копия по построению отстаёт, и финальная приёмка смотрит сам кит.

**Headless Chrome:**

- без `--virtual-time-budget` — он замораживает время, пока висит хоть один сетевой
  запрос; на странице с внешним скриптом Chrome стоит до таймаута и пишет пустой файл;
- **без** `--user-data-dir` — зависание вызывает сам флаг, а не его отсутствие. Замер на
  Chrome 152 (15.09.2026, контрольный опыт на простом локальном файле): с флагом код
  выхода 124 и 25 секунд, без флага код 0 и 2 секунды, снимок получается в обоих
  случаях. Раньше здесь было записано обратное, и на этом теряли время;
- ненулевой код `timeout` не значит «снимок не вышел» — Chrome успевает записать файл
  до того, как его убьют. Проверять надо наличие файла, а не код возврата;
- запускать асинхронно (`execFileSync` блокирует событийный цикл, а сервер поднят в том
  же процессе) и гасить через `timeout` + `pkill`.

**Длинный промпт в чат проекта** (расширение Claude for Chrome): `pbcopy < файл` →
`find` поля ввода → клик **по ref, а не по координатам** → `cmd+v` → сверить
`document.querySelector('[contenteditable="true"]').textContent` → клик по ref кнопки
Send. Печатать через `type` нельзя: переводы строк отправляют сообщение по частям.
Порог вложения — примерно 2,5 тыс. знаков: текст длиннее прилетает чипом «Pasted text»
и тогда нужна подводка «сделай всё из приложенного»; текст короче вставляется строкой,
и подводка к нему приклеится.

**Клик по кнопке Send может не сработать, и это молча стоит целого хода.** 19.09.2026 промпт
раунда 49 остался висеть в композере с прикреплённым чипом: клик по ref прошёл без ошибки,
заголовок вкладки показал значок работы, а сообщение не ушло. Понял только через двадцать минут,
когда заметил, что платформа не тронула ни одного файла. Причина: кнопка была **ниже видимой
области** — `getBoundingClientRect()` дал y=1117 при высоте кадра 827, — и расширение кликнуло
мимо.

Поэтому отправку надо **подтверждать**, а не предполагать: после клика проверять, что композер
опустел (`textContent.length === 0`). Если не опустел — жать программно:
`[...document.querySelectorAll('button')].filter(b => /Send/i.test(b.getAttribute('aria-label') || b.textContent))`
и вызывать `.click()` у последней. Этот путь сработал сразу и не зависит от прокрутки.

Отдельный признак того же: если через пять-семь минут после отправки в проекте не изменился
**ни один** файл, сообщение скорее всего не ушло. Обычно платформа начинает править файлы
в первые минуты.

**Буфер обмена общий с человеком, и `pbpaste` его не резервирует.** 19.09.2026 при отправке
раунда 46 между проверкой `pbpaste | wc -c` (6151, верно) и нажатием `cmd+v` человек скопировал
у себя постороннее, и в композер лёг посторонний текст вместо
промпта. Отправить это в чат проекта было бы и бессмысленно, и неловко.

Отсюда порядок: после вставки **обязательно смотреть композер глазами** — скриншотом области
ввода, — и только потом набирать подводку и жать Send. Длинный текст виден как чип с именем
файла и числом строк («Промпт кита, раунд 46 … 111 lines»); если вместо чипа строка или чип
чужой, надо очистить поле (`cmd+a`, `Backspace`), перезаписать буфер и вставить заново. Проверка
`pbpaste` перед вставкой полезна, но ничего не гарантирует: между ней и `cmd+v` проходит
несколько секунд, и буфер за это время может смениться.

**Буфер обходится целиком — вставкой скриптом.** 19.09.2026 при отправке раунда 73 буфер
перехватило дважды подряд, оба раза посторонним текстом,
и гонка за него была заведомо проигрышной. Способ без буфера: закодировать файл
(`base64 -i промпт.md | tr -d '\n'`), в странице раскодировать
`new TextDecoder().decode(Uint8Array.from(atob(B64), c => c.charCodeAt(0)))` и вставить
`document.execCommand('insertText', false, text)` в сфокусированный композер. Переводы строк
при этом **не отправляют сообщение** — в отличие от `type`, — а становятся абзацами ProseMirror.
Проверять надо `textContent.length` (склейка абзацев без переводов строк, то есть короче
исходника) и `innerText` (структура сохранена); длина второго редактора обязана не измениться.
Побочное отличие от `cmd+v`: чипа «Pasted text» не появляется даже на длинном тексте — промпт
ложится телом сообщения, и подводка «сделай всё из приложенного» не нужна.

**Но у способа без буфера своя цена: base64 переносится в вызов инструмента руками.** 19.09.2026
на промпте раунда 75 (8112 знаков base64) при переносе потерялось три знака, и в композер лёг
текст на три знака короче файла. Поймано сверкой длины: у файла 4296 знаков без переводов строк,
в композере оказалось 4299. Поэтому после вставки скриптом длину надо сверять с файлом всегда
(`len(текст без переводов строк)`), а не только смотреть голову и хвост. Раунд 75 в итоге ушёл
штатным путём через буфер: там содержимое подтверждается чипом с именем файла и числом строк
(«Промпт кита, раунд 75 … 102 lines» при 101 строке в файле), и переносить руками нечего.

**Порог вложения меряется знаками, а не байтами.** 20.09.2026 промпт раунда 81 на 4042 байта
лёг в композер СТРОКОЙ, а не чипом: в нём 2830 знаков, то есть ниже порога ~2,5 тыс. Раунды
75-80 при 4,5-6 тыс. байт давали чип. Поэтому после `cmd+v` надо смотреть, что получилось, и
вести себя по факту: чип — набирать подводку «сделай всё из приложенного», строка — отправлять
без подводки, иначе она приклеится к тексту. У строки есть и плюс: содержимое сверяется точно —
`textContent.length` обязан совпасть с числом знаков файла без переводов строк (2746 = 2746).

**`cmd+v` иногда не срабатывает вовсе, и это видно только глазами.** 20.09.2026 на промпте
раунда 85 после очистки композера вставка не дала ни чипа, ни текста: поле осталось пустым,
кнопка Send серой, `textContent.length` ноль. Буфер при этом был цел (`pbpaste | wc -c` 4044).
Помогло поставить каретку явно перед повтором: `c.focus()`, затем `Range` по содержимому с
`collapse(false)` и `getSelection().addRange(r)` — после этого тот же `cmd+v` лёг сразу.
Одного `focus()` недостаточно: класс `ProseMirror-focused` стоял и в неудачной попытке.

**`contenteditable` на странице ДВА, и второй — редактор readme самого кита.** Поэтому
`document.querySelector('[contenteditable="true"]')` (первый) — композер, а
`querySelectorAll(...)[1]` — документ проекта на 25 тыс. знаков. 19.09.2026 клик по ref,
который `find` уверенно назвал полем ввода, фокус композеру не дал: фокус остался на
редакторе документа (`ProseMirror-focused`), и `cmd+v` с последующим `type` ушли в никуда —
композер остался пуст. Повезло: в документ тоже ничего не легло, `readme.md` сохранил размер
26 950 и прежний etag. Но если бы легло, мы бы молча правили readme кита.

Порядок, который это снимает: перед вставкой сфокусировать поле **скриптом** —
`[...document.querySelectorAll('[contenteditable="true"]')][0].focus()` — и проверить, что
у него `data-placeholder` равен «Describe what you want to create...», а длина текста ноль.
После вставки сверять не только композер, но и длину второго редактора: она обязана остаться
прежней. Скриншот композера тоже полезен: чип «Pasted text» с числом строк виден глазами,
а поиск по `innerText` даёт ложное срабатывание — слово «pasted» есть в прошлых сообщениях.

**Каждый раунд — в новом чате (решение 23.09.2026).** К раунду 102 в чате проекта
накопилось 510 тыс. токенов контекста — платформа сама показала баннер «Start a new chat to
save 510k tokens of context». Этот контекст перечитывается на каждом ходу, и именно им
20.09 выело недельный лимит платформы. Поэтому перед отправкой каждого раунда жать New chat:
файлы проекта остаются на месте, старые чаты лежат в Chat history. Цена — у платформы нет
памяти прошлых раундов: формулировка «тот же приём, что в раунде N» больше не работает,
промпт открывается вводной в два-три предложения (кит — порт `@nuxt/ui` 4.11.1, я сверяю
DOM и пиксели с библиотекой, править только названные файлы) и несёт все факты сам.

Где кнопка: **New chat — пункт выпадающего меню под кнопкой «Chat history»** (значок в шапке
чата, `find` находит его как «Chat history button»); там же — список бесед. «Project menu» с
24.09 содержит только Rename/Duplicate/Delete, New chat из него ушёл. Чат оттуда чистый
(«Start with context»). А вот
New chat из баннера «Start a new chat to save … tokens» переносит **сводку** старого чата, и
23.09 эта сводка подала брошенный раунд 102 как незакрытую задачу — пришлось снимать её
подводкой. Поэтому новый чат открывать из меню, не из баннера.

Подводка к чипу не обязательна. 23.09 на раунде 104 скрипт вставил «Сделай всё из
приложенного» и сразу нажал Send, но ушёл один чип — текст остался в композере, видимо,
состояние редактора не успело обновиться. Платформа приняла чип за промпт и начала работать.
Значит, достаточно чипа и Send; а после отправки композер проверять на остаток и чистить
(`selectNodeContents` + `execCommand('delete')`), чтобы остаток не ушёл следующим сообщением.

**Конец хода платформы** определяется по etag `_ds_bundle.js` из `list_files(depth:-1)`:
бандл пересобирается последним, ход закончен, когда его etag свежее всех исходников.
Свежести одного бандла мало, и одинаковости трёх etag тоже. Надёжен только один признак:
**листинг не изменился между двумя проверками с паузой в три-пять минут**. 18.09.2026 за один ход
бандл пересобирался четырежды (845 507 → 846 990, потом 855 830 → 857 976 → 857 023), причём
`_ds_bundle.js`, `_ds_manifest.json` и `_adherence.oxlintrc.json` то расходились по etag, то снова
совпадали — совпадали они и на промежуточных сборках. Съёмка по любой из них мерила бы
недособранный кит. Расхождение трёх etag — полезная подсказка «точно ещё пишут», но совпадение
ничего не доказывает.
Ненадёжны два признака: стабильность размера ответа (протухший токен отдаёт 302 и тело
около 119 байт — «стабильно» по определению) и значок `✶` в `document.title`, который
гаснет посреди хода.

**И стабильность КОРНЕВОГО листинга тоже ненадёжна — ровно когда ход оборвался.** 20.09.2026
ход раунда 101 встал на недельном лимите платформы («Paused — you've hit your limit»), и
корень замер: бандл 11:45, а исходники ушли вперёд на 11:47 и пересобраны не были. Две
проверки корня с паузой в пять минут дали одинаковый ответ, я счёл ход законченным и снял
310 страниц с бандла, отстающего на правку. Расхождение было видимым и до съёмки: правило
«ход закончен, когда etag бандла свежее ВСЕХ исходников» надо применять буквально —
`list_files(depth:-1)` и сравнение максимума по исходникам с etag `_ds_bundle.js`. Исходник
новее бандла значит «ход не закончен», сколько бы корень ни стоял на месте. Цена ошибки —
целый прогон съёмки и лишний раунд, который просил то, что уже сделано.

**MCP `claude-design` при 403 `FIRST_PARTY_AUTH_REJECTED`** чинится командой
пользователя `/design-login` и переподключением в `/mcp`. Агент сам этого сделать не
может — надо просить. Встроенный `DesignSync` авторизуется так же, но для Vue-китов
бесполезен: он бандлит готовые React-компоненты, а не переводит исходники.

## Задачи

Задачи ведутся в beads (`bd`), префикс `nuxt-ui-ds`, база — на общем dolt-сервере
вместе с остальными проектами.

**MCP-сервер beads здесь сознательно не ставится — только CLI `bd`.** Скилы плагина
beads написаны под MCP и просят «инструмент `create`»; это не поломка, вместо
инструмента берётся соответствующая команда `bd`. Причина решения — рекомендация самого beads: в средах с доступом к shell (Claude Code
в их числе) CLI стоит 1–2 тыс. токенов против 10–50 тыс. на схемы MCP, а сервер сделан
для Claude Desktop, где shell недоступен. Вдобавок `beads-mcp` на PyPI ушёл в 1.2.2 при
установленном `bd` 1.0.5, а параметры между версиями переименовывались
(`from_id/to_id` → `issue_id/depends_on_id`) — рассогласование версий тихо создаёт
зависимости в обратную сторону.

**Сам `bd` держим на 1.0.5 до следующего релиза (решение 15.09.2026).** Homebrew
предлагает 1.2.2, но это не «1.0.5 плюс накопившееся»: 1.2.0 и 1.2.1 опубликованы по
ошибке без тестирования, а 1.2.2 — пересобранная линия 1.1 под старшим номером. Нужное
нам (`--brief` у `bd list`/`bd ready`, `--brief-deps` у `bd show` — короткий вывод и
экономия токенов) числится за 1.2.1 и лежит на main до нормального релиза. Обновление
вдобавок не однокомандное: у двух других баз на общем сервере есть dolt-remote, а гейт remote-migrate срабатывает по базе — их пришлось бы вести по рецепту
designated migrator, предварительно доведя синхронизацию старым бинарником.

## Beads Issue Tracker

This project uses **bd (beads)** for issue tracking. Run `bd prime` to see full workflow context and commands.

### Quick Reference

```bash
bd ready              # Find available work
bd show <id>          # View issue details
bd update <id> --claim  # Claim work
bd close <id>         # Complete work
```

### Rules

- Use `bd` for ALL task tracking — do NOT use TodoWrite, TaskCreate, or markdown TODO lists
- Run `bd prime` for detailed command reference and session close protocol

**Architecture in one line:** issues live in a local Dolt DB; sync uses `refs/dolt/data` on your git remote; `.beads/issues.jsonl` is a passive export. See https://github.com/gastownhall/beads/blob/main/docs/SYNC_CONCEPTS.md for details and anti-patterns.

## Agent Context Profiles

The managed Beads block is task-tracking guidance, not permission to override repository, user, or orchestrator instructions.

- **Conservative (default)**: Use `bd` for task tracking. Do not run git commits, git pushes, or Dolt remote sync unless explicitly asked. At handoff, report changed files, validation, and suggested next commands.
- **Minimal**: Keep tool instruction files as pointers to `bd prime`; use the same conservative git policy unless active instructions say otherwise.
- **Team-maintainer**: Only when the repository explicitly opts in, agents may close beads, run quality gates, commit, and push as part of session close. A current "do not commit" or "do not push" instruction still wins.

## Session Completion

This protocol applies when ending a Beads implementation workflow. It is subordinate to explicit user, repository, and orchestrator instructions.

1. **File issues for remaining work** - Create beads for anything that needs follow-up
2. **Run quality gates** (if code changed) - Tests, linters, builds
3. **Update issue status** - Close finished work, update in-progress items
4. **Handle git/sync by active profile**:
   ```bash
   # Conservative/minimal/default: report status and proposed commands; wait for approval.
   git status

   # Team-maintainer opt-in only, unless current instructions forbid it:
   git pull --rebase
   git push
   git status
   ```
5. **Hand off** - Summarize changes, validation, issue status, and any blocked sync/commit/push step

**Critical rules:**
- Explicit user or orchestrator instructions override this Beads block.
- Do not commit or push without clear authority from the active profile or the current user request.
- If a required sync or push is blocked, stop and report the exact command and error.

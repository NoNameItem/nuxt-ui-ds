# Стенд визуальной сверки кита с Nuxt UI

Спека: `journal/specs/2026-09-15-visual-parity-testbed-design.md`.

## Тестовый проект

- Claude Design «Nuxt UI parity» — id и адрес в `journal/projects.md`.
- Кит подключён как дизайн-система «Nuxt UI Design System» (id — `journal/projects.md`).
- Механизм бандла: **копия в проекте**, и кладётся она руками. Свежий проект создаётся пустым
  (`list_files` вернул `[]`), платформа в него ничего не подставляет: страница, сославшаяся на
  `./styles.css` и `./_ds_bundle.js` до копирования, получала 404 на оба файла, а залитый
  `probe.html` вернулся из `read_file` байт в байт, без дописанной шапки. Системный промпт
  платформы говорит то же самое: «Assets from design systems or UI kits must be copied into this
  project with `copy_files` … you cannot reference them across projects».
- Следствие для раундов правок кита: **после каждого раунда статику надо перезабрать**, иначе
  артборды рисуют старый кит. Один вызов на девять файлов:

  ```js
  copy_files({ project_id, plan_token, files: [
    { src: 'styles.css',    dest: 'styles.css',    src_project_id: '<id проекта кита>' },
    { src: '_ds_bundle.js', dest: '_ds_bundle.js', src_project_id: '<id проекта кита>' },
    { src: 'tokens',        dest: 'tokens',        src_project_id: '<id проекта кита>' }
  ] })
  ```

  `tokens` копируется папкой — семь файлов. Размеры сверяются со значениями проекта кита
  (на 16.09.2026): `styles.css` 232, `_ds_bundle.js` 790 966, `tokens/base.css` 1573,
  `tokens/keyframes.css` 7086, `tokens/palette.css` 11 747, `tokens/semantic.css` 4520,
  `tokens/theme.css` 6885, `tokens/utilities-extra.css` 230 555, `tokens/utilities.css` 213 670.

- Артборды лежат в корне проекта под теми же именами, что в `bench/artboards/`; картинка —
  `assets/demo.png`.
- `serve_url` (URL с токеном) в репозиторий не попадает: в документации только долговечный
  `open_url` проекта.

## Запись файлов: `finalize_plan` обязателен

`write_files` без `plan_token` отказывает: «available only through the native Claude Design
tool — call finalize_plan…». Одноразовый грант на проект (`needs_project_grant`) схемой
инструмента описан, но этот клиент его не выдаёт, так что порядок такой:

- `finalize_plan({ project_id, scope: 'project' })` → токен на ~4 часа на **любые** записи и
  копии в этом проекте; им же пользуются `write_files` и `copy_files`;
- удаления под проектный токен не подпадают: для `delete_files` нужен отдельный
  `finalize_plan({ project_id, writes: [], deletes: [...] })` с перечислением путей.

Размеры после заливки сверяются по `list_files` — это **сохранённые** байты. То, что отдаёт
`serve_url`, сверять с локальным файлом бессмысленно: платформа впрыскивает в каждую
страницу свой `<style data-omelette-injected>` и большой скрипт, а в каждую картинку — чанк
C2PA (`caBX`).

## Шапка артборда

Дословно из `bench/artboards/badge.html`; пути относительные от корня проекта, где лежат и артборды:
`./styles.css`, `./_ds_bundle.js`. Глобал бандла — имя пространства имён из шапки `_ds_bundle.js` (поле `namespace` в `_ds_manifest.json`). От
компонента зависит **только `<title>`** (`parity · <имя>`), всё остальное копируется как есть;
у светлого и тёмного артборда заголовок одинаковый.

Версии внешних скриптов закреплены точно, включая `iconify-icon@3.0.2`: приложение иконки из
сети не тянет вовсе (глифы вшиты в клиентский бандл `@nuxt/icon`), поэтому плавающий `@3`
двигал бы только кит-сторону, и смена минора между партиями прочиталась бы расхождением кита.

**Фон страницы артборд красит сам:**
`<style>body{margin:0;background:var(--ui-bg)!important}</style>`.

Кит везёт собственную копию базового правила `@nuxt/ui` — `tokens/utilities.css`, единственное
вхождение селектора `body` на весь кит:

```css
@layer base { body { background-color: var(--ui-bg); color: var(--ui-text);
  -webkit-font-smoothing: antialiased; -moz-osx-font-smoothing: grayscale;
  color-scheme: light; &:where(.dark, .dark *) { color-scheme: dark } } }
```

Платформа впрыскивает в каждую отдаваемую страницу беcслойное
`html,body{background:transparent}`, а беcслойное правило бьёт любой слой. Теряется ровно
**одна** декларация из четырёх — `background-color`; `color`, сглаживание и `color-scheme`
приходят сами. Шапка восстанавливает именно её и ничего больше: `color-scheme` и
`font-smoothing` дописывать не надо. `!important` стоит потому, что иначе своё правило
выигрывает только порядком в документе (специфичность равная, оба беcслойные) — стоит платформе
впрыснуть позже, и все тёмные пары разойдутся молча.

Без этого расходилась бы каждая тёмная пара: приложение красит `body` тем же правилом
`@nuxt/ui`. Дословно из `.output/public/_nuxt/entry.*.css`:

```css
body{background-color:var(--ui-bg);color:var(--ui-text);-webkit-font-smoothing:antialiased;-moz-osx-font-smoothing:grayscale;--lightningcss-light:initial;--lightningcss-dark: ;color-scheme:light}
body:where(.dark,.dark *){--lightningcss-light: ;--lightningcss-dark:initial;color-scheme:dark}
```

Отличия от кит-версии компиляционные: lightningcss развернул вложенный `&:where(.dark, .dark *)`
в отдельное правило и добавил служебные `--lightningcss-light` / `--lightningcss-dark`. Их никто
не читает — `light-dark()` не используется ни китом, ни приложением, — переносить их незачем.

Замерено на собранной странице и на артборде: светлая тема — `rgb(255,255,255)` с обеих сторон,
тёмная — `oklch(0.208 0.042 265.755)`, то есть `rgb(15,23,43)`, тоже с обеих.

Тёмный артборд отличается от светлого ровно одним — `class="dark"` на `<html>`; проверяется
командой, не на глаз:

```bash
diff <(sed 's/ class="dark"//' bench/artboards/<name>.dark.html) bench/artboards/<name>.html
```

должна быть пустой. В JSX `class` → `className` на служебных `div` раскладки; у компонентов
кита имя атрибута — как в `.d.ts`.

## Как устроена страница и артборд

- Корень страницы и артборда — `<div class="p-4 space-y-4">`. **Исключение — компонент, сам
  занимающий кадр:** оверлеи (`modal--*`, `slideover--*`, `drawer--*`), тосты (`toast`,
  `toaster--*`), каркасы (`sidebar--*`, `dashboard-*`) и собственные обёртки `container`,
  `main`. Обёртка с отступом сломала бы им раскладку, поэтому такая страница начинается
  прямо с компонента. Сейчас так устроены 65 страниц из 154 — это норма для них, а не
  отступление, и чинить её не надо. У 59 из них нет и рядов: экземпляр на странице один и
  занимает кадр целиком, поэтому ось разносится не по ячейкам ряда, а по страницам с
  суффиксом `--<вариант>` — и `rects` в JSON снимка у такой страницы пуст, сверять её
  придётся по счётчикам дифа, а не по рамкам ячеек.
- Кадр — 1280×800, **кроме страниц с суффиксом `--narrow`: у них 768×800**. Узкий кадр нужен
  тому, что библиотека показывает только ниже `lg` (1024): кнопка `DashboardSidebarToggle`
  несёт `lg:hidden`, и на 1280 ни одна пара не видела, что кит ставит её мимо `left` и `right`
  (`dashboard-navbar--narrow`, задача `nuxt-ui-ds-n33`). Ширину по имени страницы выдаёт
  `bench/scripts/viewport.mjs`, и берут её оттуда все три скрипта, открывающих страницу:
  `shoot.mjs`, `roots.mjs` и `classes.mjs`. Своя ширина в скрипте — это замер не того кадра,
  на котором снята пара. Узкая страница — копия широкой по составу плюс контрольная ячейка,
  которая совпадает и на узком кадре.
- Ряд — `<div class="flex flex-wrap gap-4 items-start">`, один ряд на строку таблицы состава
  компонента, в порядке таблицы. Этот же селектор (`.flex.flex-wrap.gap-4.items-start`) собирает
  рамки ячеек `rects` в JSON снимков (см. «Чем меряют расхождение») — отступление от него не
  только меняет вёрстку, но и лишает страницу измеримости.
- Обёртки — только те, что предписаны для конкретного вида компонента (пример: `w-64` для полей
  ввода, `h-32` для вертикальных раскладок, `w-full max-w-3xl` для блоков, `w-64 h-80` для
  открытых всплывающих поверхностей, `w-64 h-24` для tooltip). Ничего сверх: ни заголовков, ни
  подписей, ни своих классов, ни `style`, ни `ui`-переопределений.
- Значения по умолчанию не пишутся явно: если `orientation="horizontal"` — дефолт, в разметке
  его нет.
- Страница обходится без `<script setup>`, если компонент не требует управляемого состояния для
  показа содержимого (открытие оверлея, выбор файла и т. п.); когда требует — исключение и его
  причина остаются в самой странице, а не молчаливым отступлением от правила.

## Имена пропов на стороне кита

Три источника истины, которые нельзя подменять догадкой или памятью о прошлом ките:

- **оси и их значения** — `dist/docs/themes.json` по ключу компонента (`variants`,
  `defaultVariants`, `compoundVariants`);
- **пропы приложения** — `defineProps` в
  `node_modules/@nuxt/ui/dist/runtime/components/<Name>.vue`;
- **пропы и имена кита** — `<Name>.d.ts` проекта кита для имени, `<Name>.prompt.md` для примера
  использования.

Правило — два случая, не один, и они дают разные ответы.

**1. Имя объявлено в `.d.ts` — берётся объявленное, а не библиотечный синоним.**
`<Name>.d.ts` проекта кита — источник имени, `<Name>.prompt.md` — источник примера
использования. Синонимы рендерер принимает (`lib/factory.jsx` читает `props.icon` запасным
источником для слота `leadingIcon`, `props.avatar` — для `leadingAvatar`), но в артбордах они
не используются: в `.d.ts` их нет, потому что файл генерируется из слотов темы и
**недообъявляет** API, а незадокументированный путь может молча исчезнуть в следующем раунде
правок кита — и стенд запишет это расхождением кита, то есть ровно ту ошибку, ради которой он
и строится. Поэтому в артборде `leadingIcon`/`trailingIcon`, а не `icon`, и
`leadingAvatar={{ src: … }}`, а не `avatar={{ src: … }}`.

У аватара выбор имени меняет картинку, когда у компонента задан размер: через `avatar` кит
передаёт аватару ступень самого компонента (`size: av.size || options.avatarSize ||
variantProps.size`), через `leadingAvatar` значение слота уходит по общей ветке «значение слота
— объект пропов», и аватар берёт собственный дефолт темы `md`. Библиотека в обоих случаях
рисует ступень из слота `leadingAvatarSize` (`3xs` при `md`), то есть кит не прав обоими
путями, но величина расхождения зависит от написания. Для рядов «аватар по размерам» (`user`,
`chat-message` и прочие) выбран `leadingAvatar`.

**2. Пропа нет в `.d.ts` вовсе, но собственный код компонента (не общий `lib/factory.jsx`)
его читает — проп передаётся, а его отсутствие в `.d.ts` записывается находкой отдельно.**
`.d.ts` кита генерируется из слотов темы и систематически недообъявляет рабочие пути отдельных
компонентов — это не то же самое, что синоним из случая 1: здесь второго, документированного
имени для того же эффекта не существует. Артборд, который такой проп не передаёт, ничего не
рисует другого — он не воспроизводит сценарий страницы и не даёт стенду ничего проверить, а
список необъявленных пропов сам по себе ценен для кита. Известные случаи, ни один не в `.d.ts`:

| компонент | проп | где в коде читается |
|---|---|---|
| `Progress` | `modelValue`, `max` | `Progress.jsx`, собственная `slotAttrs` |
| `Chip` | `show` | `Chip.jsx`, `renderIf` проверяет `props.show !== false` |
| `Button` | `disabled` | общий путь `lib/factory.jsx` для `tag === 'button'` |
| `Separator` | `avatar` | `Separator.jsx` — деструктурируется, но не используется (код-гэп, а не путь) |
| `AvatarGroup` | `max` | нигде не читается — полностью инертен (тоже передаётся: «проигнорирован» и есть находка) |
| `Link` | `to` | `Link.jsx`, дерево — литеральный `div`, `to` в разметку не попадает |

Оба случая передаются по таблице выше без импровизации — передача «если реализация это
читает» без сверки с таблицей уже приводила к тому, что страница и артборд расходились по
составу, а расхождение, которое стенд обязан был показать сам, приходилось доказывать чтением
исходников.

**Честность.** Расхождение сторон — находка стенда, ради которой он построен: не компенсировать
её ни пропом, ни классом, ни размером холста. Причину искать не обязательно — достаточно точно
описать, что расходится; гипотезу о причине, если она напрашивается, помечать как гипотезу.
Ошибка исполнителя, записанная как расхождение кита, — худший исход из возможных, хуже
пропущенного расхождения.

## Из чего складывается состав страницы

Оси и их значения читаются из `dist/docs/themes.json`, а не выводятся из брифа задачи или
памяти о прошлом прогоне:

```bash
node -e "const t=require('./dist/docs/themes.json')['<name>'];console.log(JSON.stringify({variants:t.variants,defaultVariants:t.defaultVariants,compoundVariants:t.compoundVariants},null,1))"
```

Ось, не покрытая ни одной из сторон, — самое частое место потери: она либо добавляется рядом
(один ряд на ось при дефолтах у остального), либо получает обоснование по коду или данным, почему
она невизуальна (например: съёмка идёт с отключённой анимацией — анимационную ось не проверить;
ось требует родительского контекста, которого у страницы нет). Обоснование проверяется по
существу, отговорка не проходит. Если сумма ячеек не сходится с заявленным числом строк —
считать заново по теме, не подгонять под заявленное число.

**Дефолт у кита — из двух таблиц, не из одной.** И библиотека, и кит берут дефолт двумя путями:
тема (`defaultVariants`) и код (`default:` у пропа в библиотеке, `PROP_DEFAULTS[<имя темы>]` в
`_ds_bundle.js` — `lib/defaults.js` — у кита). `PROP_DEFAULTS` — таблица курируемая, а не
выведенная автоматически, и нужного ключа в ней может не быть. Перед тем как положиться на
дефолт кита, проверяются обе его таблицы — `defaultVariants` в `themes.json` и
`PROP_DEFAULTS[<имя темы>]`; ключ, которого нет ни в одной из двух, а у библиотеки в
`defineProps` дефолт есть, — передаётся явно с обеих сторон. Ключ, который есть хотя бы в одной
таблице, передавать не обязательно, и расхождение по нему будет настоящей находкой, а не
артефактом состава.

**Раскрытие `compoundVariants` считает записи, а не сочетания — это разные числа.** Две записи с
одинаковым набором ключей могут описывать не дубликат, а два разных состояния (одна — базовый
класс, другая — гейтованный `data-[state=…]:`/`has-data-[…]:`/`focus-visible:`). Складывать их в
одну ячейку можно, только если ни одна не гейтована состоянием; если гейтована — нужна ещё одна
отрисованная ячейка в этом состоянии, иначе часть ряда не проверяет ничего.

## Чем меряют расхождение

**Три счётчика в `dist/parity/<прогон>/diff/report.json` у каждой пары — не синонимы.**
`exactDiffPixels` — пикселей, где стороны различаются хоть чем-то (`d = |ΔR|+|ΔG|+|ΔB| > 0`); он
ловит расхождения ниже порога — полупрозрачный слой поверх слоя, чуть другой оттенок заливки.
`thresholdDiffPixels` — пикселей с `d > 30` (≈10 на канал); это и есть «различающиеся пиксели» в
обычном разговоре, и именно от него считаются регионы и доли. `diffPixels` — сумма
`thresholdDiffPixels` и `missingAreaPixels` (площади, которой на одной из сторон нет вовсе
из-за разного размера холста); годится для сортировки пар по величине беды, но цитировать его
как «различающиеся пиксели» нельзя. Отдельно — `maxChannelSum`, наибольшее `d` на паре: ноль по
порогу при максимуме в сотни — тоже расхождение, не совпадение. Порог `d > 30` калиброван не на
глаз: растровый шум (одна и та же картинка, разное округление при декодировании в разных
рендерерах) даёт максимум `d ≈ 5`, а слабейшее настоящее расхождение на практике — `d = 563`
(сдвиг линии на 1 px); между ними нет ничего, и порог стоит с запасом в обе стороны.

**Доля (`diffRatio`) — уже посчитанное поле отчёта**: `diffPixels` строки, делённый на
`canvasSize.w × canvasSize.h` этой же строки; холст — объединяющая рамка двух снимков, и у
каждой строки свой, не вьюпорт и не константа. Переносится из `report.json` целиком, всеми
строками, а не пересчитывается руками и не берётся выборочно. Доля, которой проверяется
названная причина расхождения («назвал причину — посчитай, какую долю `thresholdDiffPixels` по
регионам она объясняет; не сходится с целым — ищи дальше, доминирующая причина в отчёте стоит
первой»), считается от `thresholdDiffPixels`, а не от `diffPixels` — это разные знаменатели по
смыслу, и у каждой доли в отчёте называются и числитель, и знаменатель, и то, откуда она взята.

**Доля — характеристика пары, а не находки, и врёт тремя способами.** Она занижает, когда одна
сторона не отрисовалась вовсе: числитель тогда почти целиком состоит из `missingAreaPixels`, а
не из порогового счётчика, сравнивать по сути нечего, хотя сама доля может выглядеть скромной.
Она прячет расхождение на короткой странице: ячейка занимает малую часть большого холста, и
малый процент означает лишь малую площадь, а не близость сторон. И она прячет структурный
дефект, когда у расхождения нет пиксельного следа вовсе (см. ниже «Порядок приёмки») — доля в
этом случае честно показывает ноль, хотя дефект есть и измерим другим способом. Находка
описывается тем, что разъехалось и насколько (рамка ячейки, число пикселей, кластеры), процент
ставится рядом, а не вместо.

**`rects` в JSON снимков** (`dist/parity/<прогон>/{app,kit}/<имя>.<тема>.json`, рядом с
`errors`) — рамка каждой ячейки с ключами `row`, `i`, `x`, `y`, `w`, `h`; собирается тем же
селектором ряда, что и вёрстка страницы (`.flex.flex-wrap.gap-4.items-start`, «Как устроена
страница и артборд»). Сравнение рамок двух сторон по ключу `(row, i)` показывает, какая ячейка
разъехалась и на сколько, без счёта пикселей — это и есть инструмент проверки заявленной доли:
подтвердить, что причина одна (рамки обязаны разойтись ровно там, где названо, и нигде больше),
и отличить слепой ноль (нулевой диф при разошедшихся рамках) от настоящего совпадения (совпавшие
рамки при крупном дифе означают расхождение в заливке, а не в раскладке). **`rects` есть не у
всякой страницы** — у страницы-композиции (без рядов ячеек, например единая раскладка на всю
страницу) рамок нет вовсе, и пустой `rects` там нормальное поведение, а не находка. На таких
страницах не работает и признак «сторона схлопнулась»: страница короче вьюпорта снимается в его
высоту обеими сторонами независимо от того, что отрисовалось. Мерить остаётся коробками узлов
живого DOM (`getBoundingClientRect` по корням компонентов) — дороже, чем прочитать `rects`, и
другого способа для таких страниц нет.

**Форму расхождения даёт `regions[].clusters`, а не ограничивающая рамка области.** Рамка
называет ширину и площадь области, но объединяет все её кластеры в одну: несколько узких, далеко
разнесённых очагов (например, одинаковый элемент, повторяющийся по краям строки) рамка покажет
как одну широкую полосу, и прочитанная так находка опишет дефект неверно — и по масштабу, и по
природе. Порядок: сначала `clusters` (их число, ширина каждого, плотность
`density = pixelsInCluster / area`), и только потом рамка — для указания местоположения.

**Логический ряд состава — не физическая строка кадра.** Ряд из многих ячеек переносится
`flex-wrap` на несколько физических строк, и вертикальная дельта копится по физическим строкам
(видно по одинаковому `y` в `rects`), а не по рядам таблицы состава. Сумма дельт по строкам
обязана сходиться с разницей высот холстов сторон (`appSize.h`/`kitSize.h`) до пикселя;
несошедшийся остаток — арифметическая ошибка в разборе, а не находка.

**Равенство точных счётчиков светлой и тёмной темы при разных пороговых долях — один дефект, а
не два.** Если `exactDiffPixels` совпадает у обеих тем, а `thresholdDiffPixels` расходится —
расходится контраст, с которым один и тот же дефект проявляется на разном фоне, а не сам
дефект: в одной теме разница цвета не достаёт порога `d > 30`, в другой достаёт. Описывать его
нужно один раз, а разницу долей — контрастом. Разошёлся и точный счётчик — тогда это
действительно два случая.

**Один дефект двумя именами и два дефекта одним именем — ошибки разной цены, и вторая
опаснее.** Первая — когда находке даётся новое имя, хотя она уже описана известным классом
расхождений кита (последний отчёт прогона, `journal/reports/<дата>-parity-run.md`); цена — счёт
расхождений завышен, и киту достаются две задачи там, где чинить одно место. Ловится сверкой с
уже известными классами прежде, чем объявлять механизм новым. Вторая — когда в одном разделе
отчёта верно описаны два разных механизма, а итог приписан одному классу; цена выше: один из
двух дефектов в отчёт не попадёт вовсе, и киту его не выпишут. Завышенный счёт заметен и
поправим, пропавшая находка не заметна ничем. Признак второй ошибки: в описании одной находки
два разных «потому что» — если их два, атрибуций тоже должно быть две, даже когда симптом один.

**Диапазон легче всего перепутать по осям.** Верхняя и нижняя граница диапазона (`y: …`,
`x: …`) берутся каждая по одному полю за раз — `min(y0)`/`max(y1)` для высоты,
`min(x0)`/`max(x1)` для ширины — а не глазами по распечатке нескольких смежных чисел: числа из
соседних диапазонов совпадают по порядку величины и по типу, и подмена остаётся незамеченной
любой проверкой счётчиков.

**Ячейка отчёта без числа — расхождение, а не исключение.** Прочерк, «н/д» или пустая ячейка там,
где ожидается число, сверяется как расхождение: если поле есть в `report.json` — оно
переносится; если его действительно нет — пишется явная строка с причиной, а не прочерк,
неотличимый от «не дошли руки».

**Каждое число несёт, откуда оно взято** — пара, тема и имя поля (например
`toaster--top-left.light`, `thresholdDiffPixels`, 13784), а не «около 14 тысяч» и не «диф упал
вдвое». Доля — с явным знаменателем и от того же счётчика, от которого считаются регионы. Число
из собственного замера (координата, цвет пикселя, размер региона) — с указанием файла и темы,
на которых мерили. Число из темы — с путём внутри `themes.json` (`variants.scrollable.true`, а
не «в компаунде»). Без источника неверное число неотличимо от верного и стоит перепроверки всего
замера заново; с источником — одного взгляда в файл.

## Порядок приёмки: сначала диф, потом глаза

Осмотр листов пар (`dist/parity/<прогон>/pairs/*.png`) глазами систематически не ловит
смещения в единицы-десятки пикселей, незалитые области и мелкие глифы — партия «атомы» на
ревью показала семь расхождений, объявленных совпадением именно этим способом, включая
самое крупное расхождение партии по числу пикселей. Причина: лист пар — две склеенные
картинки с заголовками для чтения человеком, а не данные для сравнения, и восприятие на глаз
не считает пиксели.

Порядок обязателен:

1. `pnpm diff:parity --run dist/parity/<прогон>` (`bench/scripts/diff.mjs`) — считает по
   каждой паре **сырых** снимков сторон (`<прогон>/app/*.png` против `<прогон>/kit/*.png`, не
   листы пар) число различающихся пикселей по метрике `d = |ΔR|+|ΔG|+|ΔB|` (альфа отброшена),
   порог `d > 30` (~10 на канал), и рисует картинку различий в `<прогон>/diff/`.
2. Порог не подобран на глаз: на партии «атомы» растровый шум (одна и та же картинка,
   разное округление при декодировании в React-ките и в Nuxt-приложении) даёт максимум
   `d = 5`, а самое слабое настоящее расхождение партии — сдвиг линии на 1 px — даёт
   `d = 563`. Между 5 и 563 нет ничего, порог 30 стоит с запасом в обе стороны. Точный
   побайтовый счётчик (`d > 0`) печатается рядом с порогом как диагностика: скачок с единиц
   до тысяч сигналит о съехавшей съёмке (шрифты, сглаживание, рендерер), а не о ките — это
   надо заметить сразу, а не спутать с находкой.
3. Каждая пара с `diffPixels > 0` при `d > 30` — расхождение. Открыть картинку из `diff/`,
   чтобы понять **где** (полоса по Y, кластер по X — диф уже группирует), и сырые снимки
   сторон, чтобы понять **в чём**. Только после этого писать раздел «Расхождения» в отчёте
   партии — не по осмотру листов пар, а по счётчику диф-инструмента.
4. Разная высота/ширина сторон — само по себе расхождение (`missingAreaPixels` в отчёте
   `diff.mjs`), а не повод подгонять холст.

Пересъёмка после правок артборда обязательна: `diff.mjs` сравнивает то, что уже снято, и о
правке артборда не узнаёт — пока сторону не переснимут. А вот переснятую сторону он замечает
сам (ниже в этом разделе); путать эти два «сам» не нужно.

Все три скрипта (`shoot.mjs`, `diff.mjs`, `pairs.mjs`) пропускают то, что уже лежит на диске
(`diff.mjs` — пока его вывод не старше снимков, см. ниже), — это нужно для продолжения прогона
после истечения `serve_url`, но означает, что после правки состава страницы или артборда без
пересъёмки числа остаются от прежней версии. Переснимать
нужно с флагом `--force` по изменённым компонентам, например `--force --only textarea,input-tags`.
Ключ `--only` берёт и одну тему — `--force --only page-cta.dark` переснимает тёмную сторону и
не трогает светлую. Без темы флаг относится к обеим сразу: так в прогоне 2026-09-17 потеряли
готовый светлый снимок, а `page-cta` далась только с четвёртой попытки.

`diff.mjs` пересъёмку замечает сам: пара, чей снимок новее посчитанного дифа, пересчитывается
без всякого флага, а причина печатается рядом с парой (`textarea.dark (снимок app новее дифа)`).
Раньше здесь требовался собственный `--force`, и забытый флаг давал прогон, который выглядел
сделанным и был посчитан по прежним снимкам. `--force` у `diff.mjs` остаётся для другого
случая — пересчитать пару, у которой снимки не менялись (например, после правки самой метрики).
`pairs.mjs` свежесть не проверяет: лист пар — картинка для глаз, и его `--force` по-прежнему
нужен отдельно.

**Критерий приёмки:** по каждой паре число различающихся пикселей при `d > 30` равно нулю либо
объяснено записанным расхождением. «Посмотрел, выглядит нормально» не принимается.

**Регистр расхождений (`bench/ledger.yaml`, `pnpm parity:ledger`) — состояние между раундами.**
Разовый прогон говорит, что было; регистр — что из этого уже закрыто, а что остаётся незакрытой
работой, и переживает раунды правок кита (в отличие от отчёта прогона, который снимок одного
дня). Критерий окончания цикла — `unresolved: 0` на полном и непротухшем прогоне. Схема регистра,
принадлежность расхождений (`side`) и протокол раунда — в
`journal/specs/2026-09-17-kit-convergence-design.md`; этот документ их не повторяет.

**Пара, которую нельзя сравнить: чья сторона не может показать содержимое — та и решает, что
это значит.** Случаи выглядят одинаково (одна сторона пуста), а значат противоположное. Если не
может приложение — например, у настоящего компонента нет пропа для программного открытия
содержимого, — пара измеряет не кит, а собственный состав страницы, и её число ничего не значит;
такую пару помечают «статически не сравнивается» с причиной и в расхождения не включают, а факт
со стороны кита (если он рисует то же содержимое безусловно) записывают отдельной строкой. Если
не может кит — это полноценный дефект кита, обычная строка расхождений. Мерило одно: измеряем ли
мы кит или собственный состав страницы.

**Правка кит-стороны, уменьшающая диф без изменения того, что рисует библиотека, — повод
насторожиться, а не подтверждение правоты.** Композиция, добавленная в артборд только ради
сходства картинок (например, вручную собранная раскладка вместо простой передачи содержимого
компоненту), может прятать находку вместо того, чтобы её убрать — устройство кита при этом не
меняется, меняется только то, что видно на снимке. Такую правку проверяют по шаблону компонента
библиотеки (`node_modules/@nuxt/ui/dist/runtime/components/<Name>.vue`) и по тому, какому слоту
тема адресует классы, — а не по тому, что снимки стали похожи.

**Расхождение без пиксельного следа — тоже расхождение.** Ноль по всем трём счётчикам
доказывает совпадение только для тех классов темы, у которых на кадре вообще есть наблюдаемое
следствие — вопрос не «красит ли класс что-то», а «зависит ли от него хоть один пиксель на
снимке по положению или цвету». Структурная разница без такого следствия (например, разная
высота контейнера при коротком содержимом, где классу вроде `min-h-*` не на чем проявиться) —
слепой ноль: записывается находкой с прямой пометкой «пиксельного следа нет», отдельно от
настоящего совпадения, и называется в ограничениях стенда (см. «Что стенд не делает»).

**«Независимо подтверждено» — только если проверяющий не знал, где искать.** Два замера,
сделанных разными методами, независимыми **наблюдениями** не являются, если второй шёл по
указанию первого: найденный по `regions` столбец во всю высоту и найденный затем в живом DOM
лишний узел — свидетельства разной природы, и второе объясняет первое, но ошибись указание
направлением, второй искал бы там же и нашёл бы то же самое. Пиши, как было: «след найден
таким-то способом, причина установлена таким-то **по этому указанию**». Читатель сам увидит,
что свидетельств два. Слово «независимо» обещает большее и завышает надёжность ровно у тех
находок, которые проверялись по подсказке, — а это самый частый источник подтверждённых
неверностей.

Артборд, который не отрисовался (пустой `#root`, непустой `errors`), — открыть локально и найти
причину в JSX, не оставлять пустым. Ошибку вида `Cannot read properties` на стороне приложения
чинят составом страницы (обёрткой-контекстом), а не скриптом съёмки.

## Съёмка: контракт ожидания

Ждать `#root > *` недостаточно: иконки дорисовываются в shadow DOM после загрузки данных
Iconify, картинки — после декодирования. Снимок, сделанный раньше, показывает пустые квадраты
вместо иконок и белый круг вместо аватара, и это читается как расхождение кита. Контракт
ожидания:

```js
await page.waitForFunction((t) => document.documentElement.classList.contains('dark') === (t === 'dark'), theme, { timeout: 15_000 })
await page.waitForSelector('#root > *, #__nuxt > *', { state: 'attached', timeout: 30_000 })
await page.evaluate(() => document.fonts.ready)
await page.waitForFunction(() =>
  [...document.querySelectorAll('iconify-icon')].every((el) => (el.shadowRoot ?? el).querySelector('svg, span')) &&
  [...document.querySelectorAll('.iconify')].every((el) => {
    const s = getComputedStyle(el)
    return s.maskImage !== 'none' || s.backgroundImage !== 'none'
  }) &&
  [...document.images].every((i) => i.complete && i.naturalWidth > 0), null, { timeout: 30_000 })
```

Он же записан в плане у задачи 5 — тексты держатся одинаковыми, кроме одной правки
партии 10a: `state: 'attached'` вместо умалчиваемого `'visible'` на строке `#root > *`.
Найдено на `modal--*`: кит кладёт под `#root` два top-level узла — пустой обёрточный
`div` (в нём задвоенный оверлей, оба `position: absolute`, поэтому обёртка схлопывается
до высоты 0) и сам `content`. `waitForSelector` с `'visible'` ждёт видимости именно
**первого** совпадения по DOM-порядку и виснет все 30 с, хотя второй узел давно виден.
Готовность иконок/картинок/шрифтов проверяют отдельные шаги ниже; здесь достаточно, что
React вообще что-то смонтировал. Проверка `.iconify` нужна стороне приложения (там
иконки — маска на элементе, а не web-компонент), проверка `document.images` — обеим.

**Побочный эффект правки, проверенный ревью задачи 10a экспериментально:** `'attached'`
не отличает «первый узел под `#root` — невидимый стаб, второй виден» (нормальный случай
модалки) от «артборд ничего не отрисовал и висит пустой стаб» (реальная ошибка) — раньше
второй случай ловился таймаутом сам, теперь оба дают скриншот. Проверка «артборд не
отрисовался» с этой правки — **только глазами**: шаг 4 порядка приёмки («открыть
`kit/*.light.png`, ряды на месте») перестал быть формальностью и остался единственной
проверкой отрисовки. Компоненты с архитектурой `DialogRoot`/`DialogPortal`
(`modal`, `slideover`, `drawer`) особенно подвержены двум top-level узлам под `#root` —
им эту проверку глазами делать обязательно.

`colorScheme` задаётся явно на каждый снимок с обеих сторон. Тема артборда приходит из
`class="dark"` в разметке, а не из `colorScheme`, но механизмы независимы, и на стороне
приложения тему выбирает именно `colorScheme` — снимать обе стороны надо одинаково.

## Картинка `demo.png`: одна и та же 80×50 с обеих сторон

Обе стороны несут **один и тот же файл 80×50**, 652 байта, md5
`24523c09e2d906a2f3a9f592854a1357`: `bench/public/parity/demo.png` и `bench/public/parity/demo.png` в
приложении, `assets/demo.png` в проекте Claude Design.

Это **отклонение от плана**, где в таблице файлов записано 320×200 (12 922 байта). Причина —
отдающий слой платформы портит PNG: в отданном файле один байт IDAT отличается от
сохранённого, CRC чанка не сходится, поток deflate обрывается на середине, и браузер рисует
картинку частично (верхняя четверть градиента, дальше пусто). Замер на четырёх файлах: IDAT 17
и 595 байт отдаются целыми, IDAT 1471 (испорчен байт 740) и 3694 (байт 1785) — нет. Порог
между 595 и 1471 байтом IDAT; от содержимого не зависит (копия того же файла портится в том же
месте), от `direct=1` и заголовка `Accept` — тоже. Ограничение «контент детерминирован и
одинаков с обеих сторон» сильнее записанного размера, поэтому уменьшилась и сторона
приложения.

**Файл зафиксирован; пересчитывать его нельзя.** Исторически он получен так:

```python
# прогонять заново НЕ надо — результат зависит от версии Pillow, и стороны разойдутся
Image.open('bench/public/parity/demo.png').convert('RGB').resize((80, 50), Image.LANCZOS) \
     .save('demo.png', optimize=True, compress_level=9)
```

Если картинку надо залить в проект заново (проект пересоздан, файл потёрт), байты берутся
готовыми: base64 лежит в отчёте задачи 4
(`.superpowers/sdd/2026-09-16-visual-parity-testbed/task-4-report.md`), либо
`base64 -i bench/public/parity/demo.png` по уже зафиксированному файлу. После заливки сверить размер
(652) и md5 с указанным выше.

Заливка картинки идёт только inline-base64 (`local_path` в `write_files` не реализован),
поэтому чем файл меньше, тем надёжнее: 17 тыс. знаков base64 у полноразмерного файла дважды
приехали с потерей, 872 знака у 80×50 — без единой.

## Снять

    node bench/scripts/shoot.mjs --kit '<serve_url>'         # обе стороны, обе темы
    node bench/scripts/shoot.mjs --side app                   # только приложение
    node bench/scripts/shoot.mjs --side kit --local           # запасной путь: dist/kit-live + bench/artboards/
    node bench/scripts/shoot.mjs --side app --force --only page-cta.dark   # пересъёмка одной стороны

**В `--kit` идёт `serve_url` как есть, с именем файла.** Имя страницы подставляет сама съёмка
(`shoot.mjs:87`) заменой по регулярке `[^/?#]+\.html`. Плейсхолдер `PAGE` нужен только
`roots.mjs` и `classes.mjs` — у них другой разбор. 19.09.2026 в раунде 73 `PAGE` попал в
`--kit` съёмки: `.html` в URL не осталось, замена не сработала ни разу, все запросы ушли на
несуществующий `serve/PAGE`, и 33 пары подряд легли с «404» и «Timeout 15000ms» на проверке
темы — снимки при этом удаляются, так что прогон ещё и потерял готовые кадры. Признак ровно
такой: в JSON пары стоит 404 плюс таймаут первой `waitForFunction`, а `curl` по тому же
`serve_url` с настоящим именем файла отдаёт 200.

Ключ `--only` принимают все три скрипта в одной форме: `badge` — обе темы, `badge.dark` — только
названная. Отбор идёт по паре и стоит раньше проверки существования файла, поэтому снимок
второй темы под `--force` не затрагивается вовсе. Промах называется предупреждением, включая
опечатку в теме: `page-cta.darkk` — не суффикс темы, значит имя, а такого имени нет.

**`page-cta` возвращена в цикл 2026-09-19** (задача `nuxt-ui-ds-420` закрыта). С
2026-09-18 страница стояла `status: incomparable`: платформа не отдавала этот артборд
воспроизводимо — восемь попыток за два прогона, все `page.waitForFunction: Timeout`, рецепт
«пауза плюс свежий `serve_url`» не помогал, при этом соседние 312 страниц снимались, а
локальная копия с теми же байтами рисовала её за секунды. Пометка снята, потому что условие,
на котором она стояла («число по паре не добывается вовсе»), перестало выполняться: страница
снимается два полных прогона подряд. Держать её дальше значило бы подгонять регистр под
ожидаемые числа.

`serve_url` — из `render_preview` любого артборда тестового проекта; живёт около часа; при
истечении перезапросить и повторить команду с тем же `--out` — готовые файлы не переснимаются.

**Брать `serve_url` надо непосредственно перед съёмкой, а не в начале цикла проверки.** Час
жизни токена короче, чем весь цикл «дождаться конца хода платформы → залить статику → сверить
девять размеров → проштамповать → снять 310 страниц»: 20.09.2026 токен был взят в 11:15, полная
съёмка стартовала в 11:54 и в середине прогона упёрлась в истечение. Признак — тот же, что
в `CLAUDE.md`: страницы отдают 302 с телом около 116 байт, снимок падает по
`page.goto: Timeout 60000ms`, и **путь отказа удаляет уже готовый PNG**. За несколько минут
насчитался 71 таймаут, а файлов стало 185 вместо 310 — съёмка не просто перестала двигаться,
она разобрала собственный результат. Лечится перезапросом токена и повтором с `--force`;
проверять на живость надо не догадкой, а `curl` по любой странице: 200 против 302.
Тема задаётся явно на каждый снимок (`colorScheme`), системная тема машины не влияет. Локальная
копия — кэш и отстаёт от кита; финальный прогон снимает сам проект.

## Посчитать диф

    pnpm diff:parity --run dist/parity/<прогон>         # bench/scripts/diff.mjs

Разделитель `--` перед флагами не ставится: установленный pnpm передаёт его скрипту как
обычный аргумент, а все скрипты стенда разбирают флаги `parseArgs` без позиционных — форма
`pnpm diff:parity -- --run …` падает с `ERR_PARSE_ARGS_UNEXPECTED_POSITIONAL`.

Это и есть приёмка, не листы пар — критерий совпадения и три счётчика `report.json` см. в
«Порядок приёмки» и «Чем меряют расхождение» выше. Пропускает то, что уже посчитано, но пару,
чей снимок новее посчитанного дифа, пересчитывает сама и называет причину; `--force` нужен
только там, где снимки не менялись (см. «Порядок приёмки»).

## Приёмка регистра

    pnpm parity:ledger --run dist/parity/<прогон>                  # bench/scripts/ledger.mjs
    pnpm parity:ledger --run dist/parity/<прогон> --only tooltip    # вердикт по классам целевого прогона
    pnpm parity:ledger --run dist/parity/<прогон> --all             # список блокеров целиком

    KIT_SERVE_URL='<serve_url кита>' pnpm kit:pull dist/kit-listing.json   # выгрузка статики и отметка свежести

Разделитель `--` не ставится, как и у остальных команд стенда (см. «Посчитать диф»). Что
печатает команда, чем закрывается пара и какие шесть причин держат `unresolved` — в
`journal/specs/2026-09-17-kit-convergence-design.md`; этот документ их не повторяет.

Протухание пары считается от `kit.statics_copied` до времени съёмки, а время берётся из
`shotAt` в JSON рядом со снимком — его пишет сама съёмка. По mtime файла считать нельзя:
`cp -r` без `-p` ставит всем снимкам текущее время, и скопированный каталог допочинкового
прогона читался бы свежим целиком. Прогоны, снятые до появления поля, считаются по mtime, и
шапка вердикта говорит, чем посчитано. Саму отметку ставит `pnpm kit:pull` после выгрузки, и запускать
его надо после `copy_files` статики в тестовый проект (шаг 5 протокола): отметка — текущее
время, и отметка до копирования объявила бы свежими снимки, снятые с прежней статикой.

Список блокеров подрезан: по десять строк на причину, в порядке старшинства причины (`регресс`
первым), дальше хвост «…и ещё N»; `--all` печатает его целиком. Подрезка нужна ровно затем,
зачем список и читают: в первом наполнении он 292 строки «остатка», и строка регресса в нём
невидима. Авторитетный итог — строка счётчиков причин над списком, её не сокращает ничто.

Доля «в ноль N из M» считается по парам, привязанным к классу, а не по всем парам с этим
дефектом, — поэтому охват класса дополняется после раунда по новому отчёту. Требование и причина
— шаг 9 протокола раунда в спеке.

## Разобрать пару по детям корня

    node bench/scripts/roots.mjs --kit '<serve_url, где имя страницы заменено на PAGE>' --only listbox,table

Третий вопрос после «что различается в кадре» (диф) и «каких узлов нет» (счёт слотов): **где
узлы стоят**. Он оказался решающим там, где первые два молчали.

Пара `listbox` держала 2 821 139 пикселей — больше любой другой в прогоне — и три раунда не
двигалась: счёт слотов почти сходился, и в промпт уходил симптом. Разбор по детям корня
назвал причину за один прогон:

    приложение   content:div:168                                  ← один ребёнок, всё внутри
    кит          div:33 | content:div:8 | label:28 | separator:1 | item:37 | … пять раз

Шаблон элемента оказался сиблингом `content` вместо того, чтобы лежать внутри него и внутри
`group`, и выдавал `label` и `separator` на каждый элемент, хотя у обоих в дереве стоит
`if:1`. Промпт с этим разбором закрыл пару с первого раза: 2 821 139 → **388 150**, ноль
ухудшившихся пар.

Высоты в списке детей важны не меньше состава: у `page-hero` состав отличается ровно одним
узлом `body`, и именно он даёт +168 пикселей высоты корня — число сходится с прежним замером
механизма `CHILD_SLOT_ORDER` до пикселя.

Отдельной строкой печатаются положения и размеры всех `<img>`: у картинок обычно нет
`data-slot`, и обоим другим замерам они невидимы. У `page-hero` это оказалось **всем**
остатком пары: размеры трёх картинок совпадали до пикселя, высоты всех семи корней совпадали,
состав узлов сходился целиком — а первая картинка стояла у приложения в правой колонке
(x=672), у кита в левой (x=48). 922 821 пикселя диффа при нулевом `missingAreaPixels`.

Печатаются высоты **всех** корней страницы, а не только первого, и это отдельно важно: без
них «расходится везде» не отличить от «расходится в одном месте», и промпт уходит про всю
страницу вместо одного примера. У `table` пятнадцать корней из шестнадцати сошлись, а
шестнадцатый — пустая таблица — дал 48 против 312; у `pricing-plan` разница оказалась
постоянной, ровно +44 на каждой из девяти карточек, и само постоянство было подсказкой:
лишний узел или отступ, а не сломанная раскладка.

## Сравнить классы узел-в-узел

    node bench/scripts/classes.mjs --kit '<serve_url, где имя страницы заменено на PAGE>' --only alert,chip

Третий инструмент рядом с дифом и листами, и нужен он ровно там, где оба слепы. Диф говорит,
что кадры разные, и молчит о причине. Счёт узлов говорит, каких узлов нет. Но к восьмому
раунду правок кита появился класс пар, у которых **состав узлов совпал целиком**, а диф
крупный: `alert` 162/162 при 232992 пикселях, `chip` 89/89 при 13397, `form-field` 76/76 при
22584. Раунд, отправленный на симптоме («высота вдвое при совпавшем составе»), дал ноль;
этот замер назвал причину с первого прогона — у `alert` все 114 расхождений оказались узлом
иконки (коробка 20×20 против 16×16 и `display:block` вместо `inline-block`), у `chip` —
потерянным вариантом `color`.

Сравниваются тег, набор классов в обе стороны и атрибут `style`. Узлы сопоставляются по
порядку обхода внутри одного `data-slot` (`icon#3` — третий узел со слотом `icon`).

**Две ловушки, обе стоили ошибки в промпте, обе теперь ловятся машиной.**

*Первая — неостилённая сторона приложения.* Сервер замера отдавал только `index.html` и не
отдавал CSS из `/_nuxt`. Вычисленные стили и размеры на такой странице бессмысленны: коробка
иконки вышла 16×16 вместо настоящих 20×20, высота документа 1513 вместо 2560, и целый пункт
промпта ушёл в кит по ошибке — платформа потратила ход на несуществующий дефект. Признак
берётся не из «есть ли `styleSheets`», а из preflight Tailwind: он обнуляет поля `body`, и без
CSS браузер даёт 8px. Страница без стилей теперь роняет замер, а не мерится.

*Вторая — сдвиг сопоставления.* Совпадения счётчиков узлов мало: у `chip` составы совпали
(89/89), а **последовательность** слотов разошлась, и пары сравнивались со сдвигом, давая
подряд «тег div / span» и «span / div». Последовательность сверяется отдельно, и при
расхождении строка отчёта помечается — находки из такого отчёта читаются как зацепка, а не
как доказательство. Само расхождение порядка при этом тоже находка: кит выдаёт слоты не в том
порядке, что библиотека.

Общее правило после обеих: находка этого инструмента подтверждается вторым сигналом — сдвигом
дифа после раунда или прямой проверкой конкретного примера. Так подтвердился вариант `square`
у кнопки (11408 → 9052) и так не подтвердилась коробка иконки.

*Третья ловушка — того же рода, но вне инструмента: артборд не воспроизводит сценарий
страницы.* У `dashboard-search` страница стенда передаёт `v-model:open` (открыто),
`:portal="false"` и пять `groups`, а артборд — только `fullscreen`. У закрытой модалки кит не
рисует ничего: 3 узла против 67. Пара держала 1,5 млн пикселей, семь раундов правок кита
(15-19, 23) ушли впустую, и запись «ни одного сдвига ни разу» была верной числом и ложной
причиной — двигать было нечего.

Признак нашёлся не на стенде, а в приёмке тем: она писала «узлов нет: modal» на **всех семи**
doc-страницах `DashboardSearch`. Отсюда правило: **пара, которая не двигается третий раунд,
сперва проверяется сверкой пропов артборда со страницей — и только потом уходит в промпт
снова.** Сверка делается глазами по двум файлам; машинная сверка наборов имён даёт слишком
много шума (kebab против camel, слот против пропа, слова из текста абзаца) и годится только
как список кандидатов. Смотреть надо на пропы **состояния** (`open`, `defaultValue`,
`modelValue`) и **содержимого** (`items`, `groups`, `data`): именно их отсутствие делает
артборд пустым, тогда как расхождение имён обычно законно (см. «Из чего складывается состав
страницы»).

**Сплошной прогон сверки по всем страницам сделан 2026-09-19** и сразу дал три находки,
каждая — на паре из первой двадцатки по пикселям:

- `drawer--bottom-snap` и `drawer--right-snap`: артборд передавал `snapPoints` голым (то есть
  `true`), страница — `[0.5, 1]`. Признак виден и в числах: из десяти пар `drawer` восемь
  держали 12-6 700 пикселей, а обе `--snap` — 138 680 и 59 515. Правка показала настоящий
  механизм (vaul гасит подложку, пока ящик не дошёл до последней точки), после чего **обе
  страницы убраны со стенда решением человека** — см. ниже «Снап-точки drawer выведены»;
- `tree`: нет `defaultExpanded` у элементов, вместо `defaultValue` передавался несуществующий
  проп `selected`, `disabled` стоял у дерева вместо элемента — три расхождения разом;
- `navigation-menu`: артборд передавал `level` в девяти ячейках, страница не передаёт его ни
  разу.

Вывод для порядка работ: прогон стоит десяти минут и его надо делать **до** того, как большая
пара уйдёт в промпт, а не после третьего раунда без сдвига. Шум фильтруется глазами за один
проход: расхождение `icon`/`leading-icon`, `links`/`items`, `columns`/`items` законно (это
имена слотов и псевдонимы), а `snapPoints`/`selected`/`level` — нет.

## Снап-точки drawer выведены со стенда

Решение человека 2026-09-19. Страницы `drawer--bottom-snap` и `drawer--right-snap` удалены
целиком — вместе с артбордами, а не помечены `accepted`. Так же раньше поступили с ячейкой
`virtualize` у `table`.

Довод: `snapPoints` управляет **поведением** — перетаскиванием ящика между точками. Его
статический вид не выводится из разметки, только из семантики vaul: подложка прозрачна, пока
ящик не дошёл до последней точки, а панель встаёт на долю высоты окна, а не по содержимому.
Требовать этого от статического кита значит требовать воспроизвести фазу анимации.

Покрытие не пострадало: оставшиеся восемь пар `drawer` проверяют все четыре направления и
`inset` и держат 54 156 пикселей на всех восьмерых, тогда как две снап-пары держали
1 352 691 — 31,7 % дифа всего прогона.

`kit-drawer-snap-overlay` со статусом `accepted` и полем `decided` — если снап-точки когда-нибудь

## Листы и чтение

    node bench/scripts/pairs.mjs --run dist/parity/<прогон>

Лист: кит слева, приложение справа, подпись сверху. Смотреть по компоненту, сначала все
светлые, потом все тёмные — но не вместо диф-инструмента: лист поясняет, что нашёл счётчик,
а не заменяет его («Порядок приёмки» выше). JSON рядом со снимком несёт `rects` — рамки ячеек
рядов, инструмент проверки заявленной доли (см. «Чем меряют расхождение»), а не отдельный,
менее строгий гейт.

## Пиксельный итог считается без выведенных пар

`pnpm parity:ledger` печатает две строки вместо одной:

```
пикселей в сверке: 3 637 468
  вне сверки (решением): 5 109 914 на 14 парах
```

В счёт идут только пары, которые ещё выравниваются. Пары, закрытые **решением человека** —
`accepted` (pricing, changelog) и `incomparable` (page-cta), — считаются отдельно.

Причина правила измерена: 19.09.2026 кит сломал `pricing`, давно выведенный из сверки, и одна
эта поломка подняла общую сумму с 3,6 млн до 8,7 млн. Итог показал рост там, где выравниваемые
пары падали на 144 тысячи, — то есть соврал о направлении работы. Решение принял человек
(«давай не будем считать выведенные компоненты в пиксельной сумме»).

Выведенные именно **считаются отдельно**, а не выбрасываются: если такая пара ухудшится
вдесятеро, это всё равно видно строкой ниже.

## Отчёт

Файл `journal/reports/<дата>-parity-run.md`:

    # Прогон визуальной сверки <дата>
    Кит: <id>, тестовый проект: <id>, @nuxt/ui <версия>, прогон `dist/parity/<прогон>` (локально).
    ## Окружение
    Расхождения уровня страницы, отмеченные один раз: …
    ## Таблица
    | компонент | тема | статус | описание |
    статус ∈ совпадает / расхождение / несравнимо. Описание — словами, по трём классам:
    кит рисует не то; два варианта неразличимы; компонент не рисуется.
    ## Сводка
    Совпадает N, расхождение M, несравнимо K.

Известные расхождения кита на момент публикации этого документа — в последнем отчёте прогона,
`journal/reports/<дата>-parity-run.md`; они устаревают вместе с версией кита и здесь не
перечисляются.

Из отчёта — одна задача beads «выровнять кит по приложению»: в описании ссылка на файл и
сводка числом; список расхождений в описание не копируется.

## Что стенд не делает

Не ищет причин глубже механизма, не сравнивает пикселями различия hover/focus/active и других
ширин (кроме узкого кадра 768 у страниц `--narrow`), не ловит дрейф между страницами и
артбордами. Ноль в дифе означает «не различается на снимке», а
не «одинаково устроено» — структурные расхождения без пиксельного следа стенд не ловит по
построению (см. «слепой ноль» в «Порядок приёмки»). Гейт регрессии — `pnpm audit:kit`.

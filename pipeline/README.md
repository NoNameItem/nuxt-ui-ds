# Конвейер: пакет для генерации кита, выгрузка и приёмка

## Процедура

```bash
pnpm install            # или pnpm upgrade:ui — поднять @nuxt/ui до последней и nuxt prepare
pnpm nuxt prepare       # .nuxt/ui/*.ts — темы, .nuxt/ui.css — палитра
pnpm build:ds           # dist/nuxt-ui-<version>-ds.zip
```

Пакет — шесть файлов: `themes.json` (все темы одним JSON), `components-1.md` и
`components-2.md` (шаблоны Vue SFC, без `prose`), `tokens.css`, `README.md`.
Такую форму Claude Design принимает целиком. Прямая загрузка ~300 исходных файлов
(`themes/*.ts` + `components/**/*.vue`) упиралась в лимит числа файлов: десяток тем
отбрасывался независимо от размера.

### Генерация кита в Claude Design

Это генерация кита из пакета. Импорт готового кита из `kit/` в свою дизайн-систему описан в
`docs/import.md` (EN).

Делается руками в веб-интерфейсе claude.ai/design. Страница «Set up your design system»
zip не принимает: отдавать распакованные файлы из `dist/work/nuxt-ui-<version>-ds/`
(их шесть). Если и файлы не принимаются, создать дизайн-систему пустой и приложить
файлы в чате проекта, так это работало 2026-08-25 (платформа кладёт их в `uploads/`). `/design-sync` и `DesignSync` не годятся: они бандлят готовые
React-компоненты, а не переводят Vue-исходники.

Текст при создании (подставить версию из имени архива):

```text
Собери дизайн-систему из приложенных файлов. Это исходники Vue-библиотеки @nuxt/ui <version>, дизайн-система должна воспроизводить её точно, а не «в духе Nuxt UI».

Что в архиве и как это читать:
- themes.json — источник истины по всем значениям. Ключ верхнего уровня — имя компонента (button, badge, card…), внутри slots, variants (variant / size / color / orientation…), compoundVariants и defaultVariants. Значения — готовые Tailwind-классы.
- components-1.md и components-2.md — источник истины по структуре DOM: шаблоны Vue SFC всех компонентов. DOM-узлы помечены data-slot="<имя>", и это имя совпадает с ключом в slots соответствующей темы. Компоненты без data-slot — однослотовые обёртки или композиции других компонентов.
- tokens.css — палитра в oklch, CSS-переменные --ui-* для светлой и тёмной темы (селектор .dark), keyframes.
- README.md — подробные правила чтения.

Правила:
1. Значения переноси из themes.json буквально, без пересчёта, округления и выравнивания между компонентами. Если в теме "xs": {"base": "px-2 py-1 text-xs gap-1"}, это и есть xs.
2. Шкалы размеров у компонентов разные. У button пять ступеней: xs, sm, md, lg, xl; ступени 2xs нет. У badge своя шкала. Не переноси шкалы из других версий библиотеки и не придумывай ступени.
3. Цвета — только семантические роли primary, secondary, success, info, warning, error, neutral через переменные из tokens.css. Тёмная тема — через класс .dark.
4. Границы там, где в теме написано ring, рисуются ring (inset box-shadow), а не border.
5. Один компонент дизайн-системы на одну тему из themes.json, имя как в теме (Button, Badge, Card, NavigationMenu…). Компоненты, у которых есть шаблон, но нет темы (ColorModeButton, LocaleSelect, Content*), делай как композиции из уже собранных.

Что должно получиться:
- компоненты принимают пропсы variant, size, color и дают ровно те классы, что записаны в теме, включая compoundVariants и defaultVariants;
- принимают произвольное содержимое (children) и переопределение классов слотов через проп ui — это контейнеры, а не картинки;
- CSS-состояния hover:, focus-visible:, disabled:, data-[state=…] из тем работают;
- поведение оверлеев (раскрытие меню, модалки, тултипы) воспроизводить не нужно: достаточно, чтобы открытое/закрытое состояние задавалось пропом;
- иконки — Lucide (имена вида i-lucide-*), как в шаблонах;
- карточки предпросмотра для каждого компонента показывают все варианты, размеры и цвета в светлой и тёмной теме.

Как это будет проверено: темы, зашитые в собранные компоненты, будут машинно сопоставлены с themes.json по значениям. Оставь в каждом компоненте исходную тему как литерал и комментарий со ссылкой на themes/<имя>.ts, чтобы сверка была возможна. Расхождение хотя бы в одной ступени означает, что импорт не удался.
```

### Приёмка

Платформа кладёт в каждый компонент комментарий `copied verbatim from Nuxt UI …
themes/<name>.ts` и литерал `const theme = {…}`. Скрипт вынимает их из
`_ds_bundle.js` и сравнивает с `themes.json`:

```bash
node pipeline/verify-kit.mjs <URL или путь к _ds_bundle.js>
```

URL бандла — из `render_preview` (MCP `claude-design`) любого файла проекта, с заменой
пути на `_ds_bundle.js`. Норма: 112 из 112 совпали, «отличается: 0», «нет в ките: 0».
Дальше визуальная проверка: `render_preview` карточки компонента → headless Chrome
(`--headless --screenshot`, через `timeout` + `pkill`), светлая и тёмная тема.

### Что ломается при генерации и чем чинится

Темы платформа переносит точно, а вот логику из `<script setup>` теряет: рендерер
`lib/factory.jsx` обходит DOM-дерево шаблона и не знает про дефолты `defineProps`,
вычисляемые флаги `leading`/`trailing`, карту `appConfig.ui.icons`, вложенные
`DefineTemplate`/`ReuseTemplate` и примитивы reka-ui. Симптомы 2026-09-13: аватар без
круга, пустой прогресс, иконка поверх текста в инпутах, пустые хлебные крошки,
навигационное меню и пагинация. Промпт-фикс с разбором причин: `journal/prompts/docs-fix-prompt-2026-09-13.md`; второй раунд после
перепроверки (слот `base` для строковых классов, twMerge `flex-1`/`flex-col`, вложенные
`for`, `if`-узлы примитивов, CSS-переменные reka, `ReuseContentTemplate` модалок):
`journal/prompts/docs-fix-prompt-2026-09-13-round2.md`; третий раунд после проверки остальных карточек
(twMerge путает `text-pretty`/`text-center` с цветом, Boolean-пропы без default не равны false,
`data-state` у Stepper и Accordion, статические Table/AuthForm/DashboardSearchButton, `v-else-if`,
`text-default` у тёмных панелей карточек): `journal/prompts/docs-fix-prompt-2026-09-13-round3.md`; четвёртый раунд по остаткам (children попадают
в именованный слот, `v-if` по значению пропа у Separator, дубль DashboardSidebar, потерянный
заголовок навбара, `fixed` у оверлеев вылезает за артборд): `journal/prompts/docs-fix-prompt-2026-09-14-round4.md`; пятый раунд (дефолты пропов не участвуют в разрешении
вариантов, слот-элемент теряет пропы, `fixed` у оверлеев вместо `absolute`):
`journal/prompts/docs-fix-prompt-2026-09-14-round5.md`; шестой раунд — один дефект: `fixed` у оверлеев удалили,
а `absolute` не поставили: `journal/prompts/docs-fix-prompt-2026-09-14-round6.md`; седьмой раунд — дефект в сгенерированном
`tokens/utilities.css`: парные утилиты translate обнуляют чужую ось:
`journal/prompts/docs-fix-prompt-2026-09-14-round7.md`.
В бандл с тех пор добавлен `icons.json` и пункт 5 README про логику шаблона, чтобы
следующая генерация учла это сразу.

## Выгрузка кита с платформы: `kit:pull` и `kit:release`

Обе команды забирают кит с платформы заново, каждый раз. Выгрузки из рабочей копии в
`kit/` нет и не будет: иначе в релиз уходит протухшее, если в конце хода забыли
перевыкачать.

| Команда | Куда | Зачем |
|---|---|---|
| `pnpm kit:pull <листинг>` | `dist/kit-live/` | рабочая копия для отладки, приёмки и съёмки `--local`; ставит отметку свежести в `bench/ledger.yaml` |
| `pnpm kit:release <листинг>` | `kit/` | релиз после приёмки; печатает `git diff --stat kit/`, коммит отдельный и ручной, затем тег `v<версия @nuxt/ui>` (CLAUDE.md, раздел «Git») |

`kit/` отладкой не трогается и служит точкой отката.

Порядок:

1. MCP `claude-design`: `list_files` проекта кита (id — `journal/projects.md`) с
   `depth: -1`, JSON-массив целиком в `dist/kit-listing.json`. Листинг есть только в
   MCP, поэтому в скрипт он приходит файлом. Если харнесс сохранил большой ответ в файл
   сам, копировать этот файл, а не перепечатывать.
2. `render_preview` любого файла кита → `serve_url`.
3. `KIT_SERVE_URL='<serve_url>' pnpm kit:pull dist/kit-listing.json` (или `kit:release`).
   Адрес — только переменной окружения; ни на диск, ни в вывод команда его не пишет.

Отказы до выгрузки:

- листинг старше 10 минут — снять свежий;
- исходник в листинге новее `_ds_bundle.js` — ход платформы не закончен (CLAUDE.md, раздел
  про конец хода). Выходы сборки `_ds_bundle.js`, `_ds_manifest.json`,
  `_adherence.oxlintrc.json` в сравнение не входят. Не входит и `readme.md`: ни в один
  выход сборки он не попадает, а шаг платформы «Fixing design-system issues» правит его уже
  после пересборки (24.09.2026, раунд 126);
- в листинге нет `_ds_bundle.js`;
- нет `KIT_SERVE_URL` или в нём нет сегмента `serve`;
- только `kit:release`: в листинге нет файла, который git отслеживает в `kit/`. Листинг
  переносится из ответа MCP руками, и потерянная запись молча ушла бы из релиза. Если
  платформа файл действительно удалила — повторить с `--allow-removals`.

Отказы во время выгрузки — цель при этом не трогается:

- ответ не 200; 302 значит протухший токен — взять свежий `serve_url`;
- размер файла после вырезания блока `data-omelette-injected` не совпал с листингом;
- `_ds_manifest.json` называет файл (компонента, экрана, карточки, токенов), которого нет в
  листинге — запись потерялась при переносе, листинг снять заново.

Выгружаются все файлы листинга, кроме `.thumbnail`: его платформа генерирует сама и отдаёт
перекодированным. Из каждого HTML вырезается блок `data-omelette-injected`, который `serve`
вставляет сразу после `<head>`. Запись идёт во временную папку рядом с целью, цель
подменяется целиком.

## Проверка импорта: `kit:check-import`

`node pipeline/kit-export.mjs check-import <листинг>` (или `pnpm kit:check-import`)
сравнивает пути и размеры листинга проекта с `kit/`. Норма — `matched: 425 of 425`.
Сообщения английские: команду запускает пользователь по `docs/import.md`. Верхние
импорты модуля — только `node:*`, чтобы она шла без `pnpm install`; это держит тест.

## Связи с `bench/`

- приёмка читает решения «принято человеком» из `bench/ledger.yaml` (`parseLedger`,
  `acceptedPaintProblems`);
- `kit:pull` пишет отметку свежести в `bench/ledger.yaml` через
  `bench/scripts/ledger-stamp.mjs`;
- съёмка стенда берёт статический сервер из `pipeline/audit/local-kit.mjs`.

## Приёмка кита: что именно проверяется

Справочник по машинной приёмке (`pnpm audit:kit`). Пишется, чтобы проверки не
изобретались заново: у каждой здесь назван **источник истины**, **знаменатель**
(сколько на самом деле сверено) и **чего она не ловит** — последнее важнее
первого, потому что именно молчаливый пробел стоил пятнадцати раундов.

Главный принцип, из которого следует всё остальное:

> **Ожидание никогда не строится из исходников кита.** Ни из `lib/child-themes.js`,
> ни из `lib/defaults.js`, ни из дерева компонента. Только из библиотеки:
> `node_modules/@nuxt/ui/dist/runtime/components/*.vue`, темы `themes.json`,
> настоящий `tailwind-variants@3.3.1`, исходники `reka-ui`. Иначе приёмка
> проверяет кит им же самим и сходится всегда.

### Как устроен прогон

`pipeline/audit-kit.mjs` собирает локальную копию кита (`assembleLocalKit`,
`dist/kit-live` → `dist/docs/local`), поднимает HTTP-сервер на случайном
порту и открывает каждую из 118 doc-страниц в headless Chrome. Страница сама
собирает полезную нагрузку и кладёт её в `<script id="ds-audit">`: по каждому
узлу с `data-slot` — имя слота, `class`, владелец из `data-ds-component` и
вычисленные значения. Ожидания строятся до Chrome, из `<script id="ds-doc">`
той же страницы (пропы каждого примера) и из библиотеки.

Ни `serve_url`, ни токенов, ни обращений к проекту Claude Design.

Три подводных камня, стоившие времени и записанные, чтобы не повторять:

- **Chrome запускается асинхронно.** `execFileSync` блокирует событийный цикл, а
  сервер поднят в том же процессе: Chrome просит страницу, Node стоит внутри
  вызова, все 118 страниц дают «не отрисовалась за 60 секунд».
- **Без `--virtual-time-budget`.** Он замораживает время, пока висит хоть один
  сетевой запрос, и на странице с внешним скриптом Chrome стоит до таймаута.
- **`timeout: 60_000` не считает время сна системы.** Машина ушла в сон посреди
  запроса — прогон простоял 7.5 часа с 41 секундой CPU. Сторожить надо время
  последней записанной страницы, а не один вызов. *(Сторож пока внешний,
  в код не внесён.)*

Каждый пример нарисован дважды — светлая копия и тёмная. Классы у них совпадают
по построению (проверено на 2799 парах), поэтому сравнивается одна; расхождение
самих копий по классам — находка.

### Шесть проверок

#### 1. Отрисовка — `checkRendered`

Бандл кита не сообщил об ошибках, у страницы есть примеры, каждый пример
нарисовался и дал хотя бы один узел. Причина важнее следствия: у упавшего
примера узлов нет по определению, и «ни одного data-slot» увело бы искать
пустой компонент вместо исключения.

«Ни одного data-slot» спрашивается только у компонента, у которого слоты есть
в самой библиотеке (`librarySlots`). `Link.vue` рисует `ULinkBase` без
`data-slot` вовсе, и требовать слот от кита значило бы требовать больше, чем
делает библиотека.

#### 2. Классы против оракула — `checkClasses`

Самая дорогая и самая плодовитая. Оракул (`pipeline/audit/oracle.mjs`) зовёт
настоящий `tailwind-variants` на теме компонента с пропами примера и отдаёт
ожидаемый набор классов по слотам.

**Знаменатель:** ~7600 слотов сверено, ~5300 не сверено. Причины несравнения
считаются отдельно и все названы в отчёте:

| причина | законно ли |
|---|---|
| узел принадлежит другому компоненту (`data-ds-component`) | да |
| узел вовсе без метки владельца | **нет** — сравнить не с чем |
| слоты компонента с `items`, кроме корневого | да, класс зависит от элемента |
| у оракула нет ожидания для слота | да, но считается |

Таблицы, которые питают оракул (`pipeline/audit/props.mjs`), — знание о библиотеке с цитатой
у каждой строки:

- **`READS`** (38 строк) — как вариант читает проп. Библиотека пишет
  `!!props.x || !!slots.x`, а не `props.x`; передать в `tv()` сырое значение —
  значит не найти вариант вовсе. Формы: `slot`, `truthy`, `raw`,
  `icons`. Полноту стерегут `readsSelfCheck()` и `readsCoverage()` — их зовут
  и тесты, и сама приёмка **до** запуска Chrome.
- **`COMPUTED`** (3) — производные пропы, которых в примере нет: у `Button`
  это `square`/`leading`/`trailing` через `componentIcons` (дословный перенос
  `useComponentIcons`), у `Switch` — какая из двух иконок нарисована первой и
  `disabled` при `loading` (`Switch.vue:61`: `:disabled="disabled || loading"`), у
  `DashboardPanel` — `size` из `defaultSize` (`DashboardPanel.vue:30`, пропа `size` у панели нет).
  PageCard сюда не входит сознательно: `spotlight` у библиотеки на статичной странице включён
  (`useMouseInElement` на монтировании даёт `elementX = −rect.left`).
- **`SLOT_VARIANTS`** (7) — вариант, переданный в вызов **одного** слота поверх общих:
  `ui.actions({ …, orientation: 'horizontal' })` у внешнего узла Alert и Toast (`Alert.vue:69`),
  `alone` у `leadingIcon`/`chevronIcon` ChatTool и ChatReasoning (`ChatTool.vue:81, :87`),
  `step` у шагов Progress (`Progress.vue:126`). Формула отвечает за **первый** узел слота —
  его и сравнивает `checkClasses`.
  Сюда же — варианты **пункта**: `active` и `loading` у CommandPalette и `active` у FooterColumns
  считает каждый пункт сам (`active || item.active`, `CommandPalette.vue:257-283`;
  `FooterColumns.vue:45`), а в корневой `tv()` эти ключи не идут. Секции `variant-active` и
  `loading` doc-страниц кладут ключ на весь компонент, и до пунктов он у библиотеки не доходит;
  до 24.09 оракул ждал его на пунктах, а кит, читавший проп верхнего уровня, сходился с ним.
  `active` у ULink без `to` — `item.active` или `false`; совпадение маршрута на статичной странице
  не моделируется. У Breadcrumb, DropdownMenu и NavigationMenu то же самое, но записей нет:
  при `items` сравнивается только корневой слот (таблица причин несравнения в проверке 2), а
  корень эти ключи не красят.
- **`PRIMITIVE_CLASSES`** (3) — то, что примитив reka делает инлайновым стилем или атрибутом, а
  кит — классами: `flex flex-row|flex-col overflow-hidden size-full` у SplitterGroup
  (`SplitterGroup.js:506-512`), `hidden` у закрытого `CollapsibleContent` ChatTool и
  ChatReasoning (`hidden="until-found"`, `CollapsibleContent.js:82`). Каждая строка держится на
  нулевой паре стенда; добавленные классы кит обязан нести.
- **`HABITAT`** (1) — компонент, который библиотека рисует только внутри другого: UToast живёт
  в Toaster, получает `data-slot="base"` и строку `Toaster.base` через свой проп `class`
  (`Toaster.vue:97-98`, `Toast.vue:31`). Узла `root` у тоста в DOM нет; ожидание `base` — root
  тоста, слитый twMerge со строкой тостера (`habitatTokens` в `oracle.mjs`). Поле `swap`
  заменяет в ожидании класс библиотеки на класс кита — только по отклонению, которое принял
  человек: у тоста `absolute` → `relative` по классу реестра `kit-toaster-stack-in-flow`
  (accepted, decided 2026-09-23). Потеря позиционирования или `fixed` вместо него по-прежнему
  расхождение.
- **`ACCEPTED_PAINT`** (1) — не знание о библиотеке, а отклонение кита, принятое человеком:
  элемента библиотеки у кита нет, и его классы лежат на соседнем узле. Ожидание узла — склейка
  слотов (`paintedTokens`), поле `ledger` называет класс реестра со статусом `accepted` и полем
  `decided`, и без такого класса приёмка не запускается (`acceptedPaintProblems`). Единственная
  запись — Editor: корень кита несёт `root` и `base` (ProseMirror), узла `content` нет, Tiptap нет
  (`kit-editor-no-tiptap`, decided 2026-09-24). Ослаблен ровно один узел, и сколько примеров он
  покрыл, отчёт печатает в «Принятых отклонениях кита».
- **`DELEGATES`** (4) — компонент, чей корень рисует другой компонент. Класс
  корня считает тема делегата, а тема обёртки приходит к нему как `class`.
- **`CHILDREN`** (18) + **`CHILD_INTO`** (11) — дочерний компонент внутри
  разметки: его класс — своя тема **плюс** строка слота обёртки, пришедшая
  пропом `class`. `CHILD_INTO` говорит, в какой слот дочерней темы этот `class`
  попадает: у модалки это `content`, а первым в теме идёт `overlay`.
- **`CHILD_PAINT`** (3) / **`OWN_PAINT`** (2) — один узел, покрашенный строками
  двух слотов темы: у дочернего компонента и у своего узла страницы
  соответственно. `InputTags.vue:121` пишет на корень
  `ui.root({ class: [ui.base(…), …] })`, отдельного узла `base` нет; без записи
  оракул ждал на корне только `root`, и все 74 примера давали «лишние» классы
  `base`. Слияние делает `paintedTokens` настоящим `tailwind-variants`, а тест
  проверяет, что twMerge не теряет ни одного класса обоих слотов. Запись бывает функцией
  пропов: у InputMenu склейка только при `multiple` и не в режиме autocomplete — ComboboxRoot
  с `as-child` отдаёт `ui.root` узлу Anchor со слотом `base` (`InputMenu.vue:397, :402`).
- **`ICON_COMPONENTS`** (8) / **`CHEVRON_COMPONENTS`** (3) — кто считает иконки
  через `useComponentIcons`. Состав сверен с библиотекой тестом: компонент,
  начавший её звать, обязан уронить тест.

**Осознанные отклонения** (`pipeline/audit/adaptations.mjs`) — не дефекты, но
приёмка обязана их знать, иначе 872 расхождения на каждом оверлее:
`fixed` → `absolute` (компонент живёт в рамке артборда), вьюпортные единицы →
проценты, классы с произвольным свойством (`[--…]`) кит выносит в инлайновый
`style`. Адаптируется **только ожидание**: симметричная нормализация сделала бы
невидимым случай, когда кит оставил вместо адаптированного класса что-то третье.

Минимумы (`min-h-`, `min-w-`) адаптируются не в проценты, а в `dvh`/`dvw` (с 24.09):
процентный `min-height` от родителя с высотой `auto` равен нулю, и панель с `min-h-svh`
схлопывается. Основание — нулевые пары `error`, `main`, `dashboard-panel--*`,
`dashboard-sidebar--*`, а не код кита.

Библиотечный класс, стоящий у кита как есть, засчитывается без адаптации (с
24.09). Раунды 114-115 сознательно вернули `fixed` на `content` у Drawer,
Slideover и Modal и на `viewport` у Toaster — пары стенда сошлись в ноль только
так, — и прежнее правило давало на этих слотах 76 ложных расхождений. Верны оба
варианта, адаптированный и библиотечный; расхождение — третий класс или его
отсутствие.

#### 3. Классы против CSS — `checkCssPresence`

У каждого класса из DOM есть правило в `tokens/*.css`. Класс без правила
приходит из двух мест, и разговор о них разный: класс темы кита — пробел
генерации CSS, класс примера документации — то, что напишет и пользователь
артборда. Счёт общий, разделение в отчёте.

Читаются **все** файлы токенов, а не один `utilities.css`: часть значений
объявлена в `base.css` и `theme.css`, плюс `utilities-extra.css`. Проверка
обязана читать ровно то, что грузит страница.

Класс без правила, которому правила не даёт и сама библиотека, расхождением не
считается и идёт в отчёт отдельным списком (с 24.09). Ответ даёт настоящий Tailwind:
`pipeline/audit/tailwind.mjs` компилирует класс поштучно тем же `@tailwindcss/node`,
поверх `@import "tailwindcss"` и `dist/runtime/index.css` библиотеки. Так отсеялись
`align-center` (Separator), `column-1` (PageColumns) и `[&_pre_code]:font-inherit`
(Editor) — классы тем библиотеки, которые ничего не делают и у неё. CSS стенда
(`.output`) для этого не годится: в нём только то, что встретилось на страницах стенда.

#### 4. Составные свойства — `checkCompositesCss` + `checkComposites`

Статическая часть: правило-утилита, задающее `translate`/`scale`/`rotate`/
`filter`/`backdrop-filter`, не должно **смешивать** литеральные части с
`var(--tw-*)` — иначе применённая следом утилита читает переменную, которую
первая не присвоила, и обнуляет чужую ось. Сканируется весь CSS **один раз**,
не по страницам: иначе одно смешанное правило попадает в отчёт 118 раз.

Формулировка «переменную никто не присваивает» тут не работает — такие
переменные объявлены через `@property` с `initial-value`, и она даёт 385
ложных срабатываний.

Динамическая часть: у узла с обоими `-translate-x-*` и `-translate-y-*`
измеренный `translate` не должен иметь нулевую ось.

#### 5. Числа против объявленных значений — `checkDeclaredValues`

Класс на месте — но действует ли он. Сравниваются не префиксы классов, а
**объявления их правил**: Tailwind v4 пишет `padding`, `padding-inline`,
`padding-block`, и таблица префиксов мимо них проходила.

Два независимых заслона от ложных расхождений, оба нужны:

1. **За свойство отвечает ровно один класс.** `COMPARABLE` отвечает на вопрос
   «что сверять», `OWNS` — «что влияет». Роли разведены, а не слиты в одну
   таблицу: дописать `min-width` в `COMPARABLE` — это 1015 ложных расхождений.
2. **Измеренное значение — строго число с единицей.** `parseFloat('96px 64px')`
   молча берёт 96; строгий разбор даёт NaN, и сравнение честно пропускается.

Отдельно — сканер `ruleBody`: класс считается владельцем правила, только если
он **субъект** селектора. Прежний поиск `.имя[^{]*\{` приписывал классу `group`
правило его потомка — 1597 фантомных кандидатов и 479 подавленных сравнений.
Запятая субъектности не рвёт (`.max-w-full,.max-w-screen{…}`).

Второй владелец свойства бывает и у **родителя**: правило `[&>button]:py-0` или
`*:my-5` пишет детям (`childRuleBodies`). У InputNumber vertical узел `increment` несёт
`[&>button]:py-0` из темы, и кнопка с объявленным `p-1.5` мерит padding 0 и в библиотеке;
до 24.09 это давало 4 ложных расхождения. Родитель — ближайший предшествующий узел со
слотом на уровень выше (`depth` считает только предков с `data-slot`), так что ошибка
возможна только в сторону лишнего снятого сравнения.

Знаменатель: объявлений-кандидатов, из них давших хотя бы одно сравнение, и
всего сравнённых значений — три разные величины, делить их друг на друга
нельзя.

#### 6. Отсутствующие узлы — `checkNodes`

Проверки 2–5 сравнивают **классы у тех узлов, что есть**. Узел, которого кит не
нарисовал, не виден ни одной из них: сравнивать нечего, расхождения не
возникает. Это тот класс дефектов, который виден глазами.

Ожидание — из `<template>` библиотечного SFC (`pipeline/audit/template.mjs`).
Слоты делятся натрое:

| множество | сколько | проверяется |
|---|---|---|
| рисуется всегда | 147 | у каждого примера |
| рисуется у открытого экземпляра | 11 | там, где пропы примера его открывают |
| под условием | 616 | **нет** |

Четыре правила разбора, каждое закреплено тестом, потому что каждое —
пойманная ошибка:

- левая граница у `data-slot`: иначе ловится `:data-slot="$attrs[…] ?? 'root'"`;
- `v-else` без значения: у `<tr v-else>` строка атрибутов кончается сразу за
  именем, закрывающий `>` съеден разбором тега;
- `createReusableTemplate`: Define-половина на месте не рисует ничего
  (Header `left`/`right`, Sidebar `body`/`inner`, PricingTable `tierWrapper`);
  имена читаются из script-блока, а не угадываются по виду `Define…Template`;
- примитивы `reka-ui` под `Presence` (`CollapsibleContent`, `ComboboxContent`)
  и `TabsIndicator`, которому нужна измеренная ширина активной вкладки. С 24.09
  там же `UModal` (контент под Presence по `open`, `DialogContent.js:47`) и явный
  `<Presence :present="showAutoScroll">` ChatMessages, который включает замер
  прокрутки, а не пропы, — его `viewport` не ждут никогда;
- `data-slot` на теге компонента без своего элемента узла не даёт (`NO_ELEMENT`):
  корень UModal — `DialogRoot`, и `data-slot="modal"`, повешенный на тег в
  DashboardSearch, в DOM не попадает. Замерено на стенде: у открытого
  dashboard-search слоты overlay, content, … и ни одного modal.

Сдвиг знаменателя от этих двух правил (24.09): безусловных слотов 135 → 133
(`modal` у DashboardSearch, `viewport` у ChatMessages), под условием 558 → 559.

Узел **прозрачного** компонента засчитывается слоту страницы, хотя владелец у
него чужой. Прозрачный — библиотечный SFC без единого `data-slot` в шаблоне
(`UContainer`): в библиотеке его корень и есть слот обёртки (`Banner.vue:109`
вешает `data-slot="container"` на `UContainer`), а кит честно метит узел
владельцем `Container`. Список не пишется руками — `transparentComponents()`
читает исходники из `node_modules/@nuxt/ui` и ищет в них `data-slot` напрямую, а не
через разбор: разбор отбрасывает `data-slot` на теге UModal, и DashboardSearch с
ContentSearch выглядели бы прозрачными. Тот же признак решает, спрашивать ли у
страницы «ни одного data-slot» (`librarySlots`).

Namespace-теги (`Component.Content`) разбираются по последней части имени;
состав всех 30 частей закреплён тестом, чтобы новый примитив не уехал из
проверяемого множества молча.

### Гейты до прогона и в тестах

- **`readsCoverage()`** — пара «страница + вариант», которую тема объявляет
  булевой, а `READS` не покрывает, роняет прогон **до** Chrome. Иначе это
  выясняется через двадцать минут, а на чистом клоне не выясняется вовсе.
- **`readsSelfCheck()`** — опечатка в имени формы уходит в `default` ветки
  `switch`, то есть ведёт себя как отсутствие строки, и молчит.
- **Состав `ICON_COMPONENTS`** сверен с библиотекой: компонент, начавший звать
  `useComponentIcons`, роняет тест.
- **Состав namespace-частей** сверен с библиотекой (проверка 6).
- **`missingKitImports()`** — локальная копия кита не собирается молча неполной.
- **146 тестов**, `node --test 'pipeline/tests/*.test.mjs'`. Обратите внимание:
  `node --test <каталог>` на Node 26 падает, нужен глоб.
- **`pipeline/verify-kit.mjs`** — отдельно от приёмки: сверяет темы, зашитые в
  собранный платформой `_ds_bundle.js`, с нашим `themes.json` по значениям, а
  не по названиям.

### Чего приёмка не ловит — читать перед тем, как верить нулю

1. **616 слотов под условием.** Пропавший спиннер раунда 15
   (`isLeading && leadingIconName`) — оттуда, и проверка 6 его бы не заметила.
   Замер: из 470 выражений `v-if`/`v-else-if` на узлах с `data-slot` 76
   читаются только из пропов, 231 — из `slots.x` (тоже вычислимо: плашка слота
   отличима по `$slotMark`), 92 — из полей элемента, 4 — состояние reka. Около
   300 достижимы таблицей «страница + слот → предикат». Это следующий срез.
2. **Порядок узлов и вложенность.** Сравнивается множество слотов, не дерево.
3. **Цвета.** Светлая и тёмная копии сверяются между собой по классам, но
   измеренный цвет ни с чем не сверяется.
4. **Состояния.** Ховер, фокус, active — по решению пользователя в макете не
   нужны, и классы с двоеточием из проверки 5 исключены.
5. **Страница без темы** — `Icon`, одна. Проверка 2 на ней не выполнялась.
6. **`readsCoverage` не ходит по вариантам темы делегата.** Записанный пробел.
7. **Каскад.** `ruleBody` возвращает первое субъектное правило, а браузер
   применил бы последнее. На живых данных классов с двумя субъектными
   правилами 39, и расходятся они только цветами. Честная починка требует
   выстроить порядок склейки файлов по порядку импорта.

### Как читать отчёт

`dist/audit/report.md`. Сверху — число расхождений по проверкам, снизу два
раздела, без которых верхнее число обманчиво:

- **«Классы без правила по происхождению»** — из тем кита или из примеров;
- **«Не проверялось»** — все знаменатели: страниц без темы, узлов чужих, узлов
  без метки, слотов сравнено и не сравнено, охват проверки 5, охват проверки 6,
  страниц, отрисовавшихся со второй попытки.

Каждая секция отчёта обрезана до двадцати записей. Полный список — в
`dist/audit/failures.json`, по записи на расхождение с полями `page` и `check`;
группировать и считать остаток надо по нему, а не по `report.md`.

**Отчёт меряет локальную копию, а не сам кит.** Копия собирается из
`dist/kit-live`, и без свежей выгрузки приёмка молча проверяет прошлый
бандл: 24.09 отчёт на 482 расхождения включал исправленное в ките раундами
раньше. Перед прогоном — `pnpm kit:pull`, шаг 5 в `bench/rounds.md`.

**У компонентов с `portal` doc-страница рисует примеры с `portal: false`**
(`pipeline/lib/docs.js`, `Section` → `Row`), как на стенде. Иначе открытая панель
уходит в `document.body` — и у кита, и у библиотеки, — а приёмка собирает узлы
только внутри ячейки примера и пишет «ни одного data-slot». Явный `portal` из
примера сильнее. Признак — строка `portal` в `propsTable` компонента; сегодня
таких 12.

Ноль расхождений без этих знаменателей читается как «сверено» — ровно это
чтение и держало пробел с отсутствующими узлами незамеченным пятнадцать
раундов.

### Когда обновится Nuxt UI

Код приёмки переживает обновление, таблицы фактов — нет. Разделение
количественное, а не на глаз:

| | объём | что с ним делать при обновлении |
|---|---|---|
| машинерия (прогон, оракул, сканер CSS, разбор шаблона, проверки) | 1829 строк | ничего, работает как есть |
| таблицы фактов о версии | ~160 строк | пересверить, каждую роняет свой гейт |
| цитаты вида `Component.vue:117` в комментариях | 64 | номера строк уедут молча |

Писать заново нечего: ни одна проверка не знает про 4.11.1. Оракул зовёт
настоящий `tailwind-variants` на теме, которую отдал сам кит; сканер CSS ищет
правило по имени класса; разборщик шаблона читает SFC той версии, что лежит в
`node_modules`. Версия входит только в таблицы, и **у каждой таблицы есть
гейт, который падает до того, как прогон успеет соврать**.

#### Порядок, в котором всё ломается

Сверху вниз — так и чинить, каждый следующий гейт имеет смысл только после
предыдущего.

1. **`pnpm build:docs` → `assertVersionMatch`.** «@nuxt/ui X не совпадает с
   тегом доки v4.11.1». Поднять `DOCS_TAG` в `pipeline/doc-pages/fetch-docs.mjs`;
   каталог кэша ключуется тегом, так что чужой кэш не подхватится.
2. **`assertDocsComplete` / `MIN_MD_FILES`.** Порог полноты каталога доки — он
   же ловит обрыв загрузки.
3. **Состав страниц.** Появившийся компонент даст новую страницу, исчезнувший —
   уроненные строки таблиц (см. ниже). Кит надо пересобрать и залить заново:
   `pnpm build:ds` → импорт в вебе → `pnpm verify:ds` (сверяет темы бандла
   с нашим `themes.json` по значениям, не по названиям).
4. **`node --test 'pipeline/tests/*.test.mjs'`.** Здесь падают гейты состава:
   `ICON_COMPONENTS` против списка компонентов, зовущих `useComponentIcons`;
   namespace-части против шаблонов; фикстуры; имена.
5. **`readsCoverage()` — до Chrome, роняет сам прогон.** Печатает поимённо:
   пара «страница + вариант», которой нет в `READS`; строка `READS`, не
   встретившаяся ни на одной странице; устаревшие `COMPUTED`, `DELEGATES`,
   `CHILDREN`; тема делегата или дочернего, которой нет в `themes.json`.
   Пустой обход тоже считается проблемой — «проверять было нечего» не то же
   самое, что «всё сошлось».
6. **`pnpm audit:kit`.** Проверка 6 первой скажет, появился ли новый отложенный
   примитив: узел, который шаблон рисует безусловно, а кит не рисует. Разбирать
   так же, как разбирались первые девять кандидатов, — по шаблону библиотеки,
   а не по коду кита.
7. **Визуальная сверка.** После нового кита пересоздать или переподключить тестовый
   проект Claude Design (`bench/README.md`, «Тестовый проект»), перезалить артборды и
   повторить прогон `shoot.mjs` → `diff.mjs` → листы пар (`pairs.mjs`) → отчёт
   в `docs/notes`. **`diff.mjs` стоит перед листами, и порядок здесь не косметика:**
   осмотр листов глазами систематически не ловит смещения в единицы-десятки пикселей —
   партия «атомы» объявила совпадением семь расхождений подряд, включая крупнейшее
   в партии. Лист пар отвечает на вопрос «где смотреть», а на вопрос «есть ли
   расхождение» отвечает счётчик.
8. **Расхождения классов.** Дальше как в раундах: причина, измерение, промпт.

#### Чего гейты не ловят — проверять руками

- **Компонент, которому понадобилась формула, которой нет.** Ровно случай
  раунда 15: кит начал рисовать спиннер, `Button` стал читать
  `leading`/`trailing`, и ни один гейт этого не потребовал — формулу пришлось
  добавлять по следам расхождения. `COMPUTED` стережётся только на
  устаревание, не на нехватку. Общее решение — таблица предикатов для 616
  условных слотов; пока его нет, это ручная сверка `tv()` у изменившихся
  компонентов.
- **64 цитаты `Component.vue:117`.** Номера строк уедут при любой правке
  библиотеки, и комментарий будет указывать не туда. Само по себе ничего не
  ломает, но сбивает следующего читателя — при разборе расхождения цитату
  стоит перепроверять, а не верить.
- **Версия `reka-ui`.** Таблица отложенных примитивов ссылается на
  `dist/…/CollapsibleContent.js:71-77` в reka 2.10.4. Гейта на версию reka нет;
  поведение изменится — увидим находкой проверки 6, но не раньше.
- **Осознанные отклонения** (`adaptations.mjs`): `fixed` → `absolute`,
  вьюпортные единицы → проценты. Это наши решения, а не факты библиотеки, —
  после обновления их надо подтвердить глазами, гейт тут неуместен.
- **Шкала размеров.** Между версиями ступени расходятся: имена (`xs`, `sm`)
  переносить вслепую нельзя, сверять надо значения — паддинг, шрифт, иконку.
- **Формулы шаблонов** (`SLOT_VARIANTS`, `PRIMITIVE_CLASSES`, `HABITAT`, `OWN_PAINT`,
  `NO_ELEMENT`). Каждая — пересказ конкретной строки шаблона библиотеки или reka с
  цитатой. Гейта на их устаревание нет: после обновления перечитать цитаты. Урок 24.09:
  формула, написанная по аналогии с соседней (hasContent у ChatReasoning скопирован с
  ChatTool), ошиблась в первом же прогоне — сверять надо с исходником каждого компонента.

#### Что стоит прогнать одной командой

```
pnpm build:docs && pnpm test && pnpm audit:kit
```

Первая падает на версии доки, вторая — на составе таблиц, третья — на
покрытии `READS` ещё до Chrome. Если все три прошли, обновление дальше
разбирается уже по отчёту, а не вслепую.

# Nuxt UI {{version}} — источник для дизайн-системы

Дизайн-система строится ИЗ ЭТИХ ФАЙЛОВ — не из документации, не из скриншотов и не
из общих представлений о том, как выглядит Nuxt UI.

| Файл | Что это | Роль |
|---|---|---|
| `themes.json` | {{themes}} тем компонентов: слоты, варианты, размеры, цвета — значениями в виде Tailwind-классов | **Источник истины по всем значениям** |
| `components-1.md` … `components-{{parts}}.md` | Шаблоны {{components}} компонентов (Vue SFC) | **Источник истины по структуре DOM** |
| `tokens.css` | Палитра (`--color-*`, oklch), CSS-переменные `--ui-*` для светлой и тёмной темы, keyframes | Палитра и семантические роли |
| `icons.json` | {{icons}} дефолтных иконок `appConfig.ui.icons` (`chevronDown`, `check`, `close`, `loading`…) | Подстановка там, где шаблон читает `appConfig.ui.icons.X` |

Ключ верхнего уровня в `themes.json` — имя компонента (`button`, `badge`, `card`),
значение — объект со `slots`, `variants`, `compoundVariants`, `defaultVariants`.
Это чистая тема библиотеки версии {{version}}, без проектных переопределений.

## Как читать

1. **Значения берутся из `themes.json` буквально.** Если в теме записано
   `"xs": { "base": "px-2 py-1 text-xs gap-1" }` — это 8px по горизонтали, 4px по
   вертикали, шрифт 12px и зазор 4px. Ничего не пересчитывайте и не округляйте.

2. **Структура берётся из шаблонов.** У большинства компонентов DOM-узлы помечены
   `data-slot="<имя>"`, и это имя совпадает с ключом в `slots` темы: узел
   `data-slot="body"` получает классы из `slots.body`. Компоненты без `data-slot` —
   либо однослотовые обёртки (`<Primitive :class="ui(...)"><slot/></Primitive>`), либо
   делегируют другим компонентам, либо не рисуют DOM вовсе.

3. **Шкалы размеров у компонентов разные, и выравнивать их нельзя.** У `button` пять
   ступеней: `xs`, `sm`, `md`, `lg`, `xl` — ступени `2xs` НЕТ. У `badge` шкала своя и с
   кнопочной не совпадает. Не переносите шкалы из других версий библиотеки.

4. **Цвета — только семантические роли** (`primary`, `secondary`, `success`, `info`,
   `warning`, `error`, `neutral`) через переменные из `tokens.css`. Значения для тёмной
   темы там уже есть (селектор `.dark`).

5. **Логика шаблона — часть компонента, а не только его DOM.** В `<script setup>` каждого
   шаблона есть `defineProps` с дефолтами (`orientation: "horizontal"`, `size`, `variant`),
   вычисляемые флаги (`isLeading = (icon && !trailing) || (loading && !trailing) || leadingIcon`,
   `isTrailing` аналогично), дефолтные иконки из `appConfig.ui.icons` (см. `icons.json`)
   и вложенные шаблоны (`DefineTemplate`/`ReuseTemplate`). Всё это надо воспроизвести:
   булевы варианты темы (`leading`, `trailing`, `loading`, `active`, `highlight`) выводятся
   из пропсов так же, как в шаблоне; узлы `<component :is>` рендерятся как элемент со своим
   слотом, а не пропускаются; компоненты на примитивах reka-ui (Pagination, Progress,
   Select, Tabs, Accordion…) получают минимальную статическую реализацию: элементы,
   `data-state`, `data-orientation`, inline-стиль индикатора.

6. **Границы у компонентов — `ring` (inset box-shadow), а не `border`**, там где так
   написано в теме. Это влияет на раскладку: `ring` не занимает места в box-model.

## Что должно получиться

Компоненты, у которых:
- пропсы `variant`, `size`, `color` дают **ровно те классы**, что записаны в теме;
- принимается произвольное содержимое (children) — это контейнеры, а не картинки;
- работают состояния `hover:` / `focus:` / `disabled:` / `data-[state=…]`, уже
  описанные классами в темах;
- поведение оверлеев (раскрытие меню, модалки) воспроизводить не нужно — достаточно,
  чтобы состояние задавалось пропом.

## Как это будет проверено

Темы в получившейся дизайн-системе будут сопоставлены с `themes.json` машинно, по
значениям, а не по названиям ступеней. Расхождение хотя бы на одну ступень означает,
что импорт не удался.
